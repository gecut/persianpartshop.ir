# گزارش اجرای کاتالوگ مشترک و بازسازی دریافت داده

تاریخ: ۲۰۲۶-۱۱-۰۹

## نتیجه

بارگیری ۲۴ محصول اول و تکمیل متوالی صدتایی، منبع مشترک محصولات در Query Cache، جست‌وجو و QR محلی، بازخوانی تدریجی، جداسازی حساب و حذف دریافت‌های مستقل پیاده شد. انتخاب و مقدار محلی‌اند؛ availability در ادامهٔ کاتالوگ و تأیید مقادیر نهایی اجرا می‌شود. ظاهر و اجزای موجود حفظ شدند.

تغییرات موجود workspace در آغاز کار، از جمله اصلاحات تأمین و انبار، مبنا بودند. تغییر هم‌زمان حذف Playwright/E2E و انتقال تست واحد به `apps/web/tests` با تأیید صریح کاربر حفظ شد؛ فایل‌ها و وابستگی حذف‌شده بازیابی نشدند.

## مالکیت و رفتار

- `apps/web/src/features/products/catalog-coordinator.ts`: یک مالک شبکه، داده فقط در Query Cache؛ cursor، scope، نسل، نسخهٔ خواندن، deduplication، pause/resume، retry محدود و حذف پس از پایان موفق بازخوانی.
- `catalog-data.ts`: مصرف مشترک و دریافت گروهی اقلام مفقود؛ مصرف‌کنندگان اقلام منتخب تمام کاتالوگ را دوباره map نمی‌کنند. بارگیری پس‌زمینه در حالت hidden/offline، نوشتن حساس و فعالیت foreground متوقف می‌شود؛ شروع سرد بخش اول منتظر بررسی session نمی‌ماند.
- `product-store.ts`: nuqs مالک URL؛ بعد از تکمیل، فیلتر و مرتب‌سازی محلی؛ پیش از تکمیل، نتیجهٔ سروری با IDهای جدا و رکوردهای مشترک.
- QR فقط برای customer دارای مجوز، شاخص SHA-256 دارد. کد خام و قیمت عمده در DTO مشترک نیستند. کد ناشناخته با lookup مستقیم بازیابی می‌شود. لغو مجوز محلی در بازبینی نشست اعمال می‌شود؛ سرور عملیات را مستقلاً مجازسنجی می‌کند.
- session بدون polling و بدون syncProfile به‌ازای mount هر هوک است. پروفایل، سفارش و طرح، نسخهٔ موازی در store ندارند. mutation ثبت سفارش مشترک و پاسخ mutation مبنای cache همان موجودیت است.
- سبد، تعیین مقدار، درخواست تأمین، جزئیات سفارش، سفارش مجدد و محصولات طرح‌ها از منبع مشترک استفاده می‌کنند. اطلاعات تاریخی فاکتور از snapshot سفارش باقی می‌ماند.
- تأیید موجودی هم‌زمان deduplicate می‌شود؛ ویرایش، تغییر حساب یا حذف انتخاب، بررسی منسوخ را لغو می‌کند. idempotency و پیش‌نویس‌های بازیابی حفظ شده‌اند.

## API و CMS

- `catalog.syncPage`، `catalog.getByIds`، `catalog.browse` و `catalog.facets`؛ DTO و ورودی‌ها در `packages/contract`.
- مسیرهای جدید کش مشتری احراز هویت می‌خواهند؛ API قدیمی کاتالوگ باقی است. نشست منقضی به کاتالوگ ناشناس داخل کش مشتری تبدیل نمی‌شود.
- cursor روی createdAt و ID و مرز آغاز پیمایش است. کامل‌بودن یعنی پایان پیمایش، نه snapshot تراکنشی قیمت و موجودی.
- scope شامل حساب/نقش، دسته‌های مجاز، markup، محدودیت موجودی/خرید و QR است. تغییر scope داده و شاخص قبلی را پاک و queryهای وابسته را بازنشانی می‌کند.
- CMS شناسه‌های browse و طرح را قبل از pagination انتخاب می‌کند؛ مجوز، موجودی یک انبار، مرتب‌سازی قیمت مشتری و تقدم طرح‌های جاری در query سرور اعمال می‌شوند.
- context سند حساب را برای handlerها بازاستفاده می‌کند. محصول projection مشخص و depth محدود دارد. availability از map برای lookup محصول و موجودی انبار استفاده می‌کند.
- transport نتیجهٔ decodeشدهٔ oRPC را بررسی می‌کند؛ clone/بافر کاملِ دوم حذف شده است. timeout تا پایان decode برقرار است؛ خطای دیررس حساب قبلی نمی‌تواند حساب بعدی را خارج کند. Forbidden کسب‌وکار با ban اشتباه نمی‌شود.

## شواهد اجرای فعلی

| بررسی | نتیجه |
|---|---|
| `pnpm --filter @persianpart/web test:catalog:unit` | ۱۰ موفق، ۳۳ assertion |
| `pnpm --filter @persianpart/api test` | ۳۴ موفق، ۵ تست زندهٔ opt-in اجرا نشدند |
| `pnpm --filter @persianpart/api typecheck` | موفق |
| `pnpm --filter @persianpart/web build` | موفق؛ هشدار قبلی اندازهٔ chunk باقی است |
| `pnpm --filter @persianpart/cms test:hardening` | ۷۷ موفق |
| `src/endpoints/catalog-browse.integration.test.ts` با PostgreSQL | موفق؛ دیتابیس موقت مجزا با migrationهای واقعی و ۶۵۰ محصول؛ سپس حذف همان دیتابیس |
| diff-check فایل‌های مرتبط | موفق |

تست PostgreSQL جست‌وجوی SKU/تگ، فیلتر ترکیبی، مجوز دسته، موجودی exact/inquiry، ترتیب قیمت و pagination، پارامترگذاری SQL، مجوز endpoint داخلی و ترتیب/مالکیت صفحه‌بندی طرح‌ها را بررسی کرد.

برای بازاجرای تست PostgreSQL، `CATALOG_TEST_CONTROL_URI` را به دیتابیس `postgres` روی localhost بدهید و `pnpm --filter @persianpart/cms test:catalog:postgres` را اجرا کنید. تست فقط دیتابیس تازه با نام `catalog_read_test_<uuid>` می‌سازد و حذف می‌کند؛ این تست روی دیتابیس عملیاتی داده نمی‌نویسد.

Typecheck کامل CMS موفق نیست: ۸ خطای TS2345 در فایل ازپیش‌موجود و دست‌نخوردهٔ `apps/cms/src/_schema-inspect.test.ts`، خطوط ۱۹۷، ۲۰۷–۲۱۰، ۲۸۱–۲۸۲ و ۳۸۷، مربوط به ورودی ساخت warehouse-stock باقی است. خطای دیگری در خروجی نهایی این بررسی گزارش نشد. این گزارش، سبزبودن typecheck کل monorepo را ادعا نمی‌کند.

## بررسی مرورگر پیش از حذف تأییدشدهٔ harness

آخرین اجرای کامل Playwright: **۲۲ موفق، ۱ آزمون ثبت زنده skipped**. این بررسی پیش از آخرین اصلاح مرز خطای احراز هویت در transport و پیش از حذف harness انجام شد؛ پس از حذف، تکرار آن در وضعیت فعلی repository انجام نشده است. مرز جدید احراز هویت با ۴ تست واحد مستقل و typecheck/build بررسی شد.

سناریوهای موفق مرورگر شامل نمایش و انتخاب بخش اول با batch دوم معلق، ادامهٔ بارگیری ۶۵۰ محصول پس از ناوبری، جست‌وجوی محلی محصول دوردست، صفر RPC دوره‌ای در ده دقیقهٔ شبیه‌سازی‌شده، بررسی دو مرحله‌ای موجودی، اسلایدر محلی، idempotency پس از قطع شبکه، بازیابی پیش‌نویس، تغییر حساب و تب، سفارش مجدد، درخواست تأمین، worker update و بازگشت اسکرول بودند. تصاویر در عرض‌های ۳۶۰ و ۱۲۸۰ و عدم overflow بررسی شدند.

## بررسی HTTP واقعی محلی

CMS توسعه برای ثبت endpointهای جدید restart شد؛ API توسعه نیز با کد جاری در پورت ۵۱۷۵ اجرا شد. `push: false` برقرار بود؛ هیچ migration یا seed عملیاتی اجرا نشد.

خواندن با JWT معتبر مشتری از مسیر Hono → Payload → PostgreSQL انجام شد. session و syncPage و plan/list و browse پاسخ ۲۰۰ دادند؛ scope نشست و کاتالوگ برابر بود و کد خام/قیمت عمده در DTO مشترک وجود نداشت.

نمونهٔ یک اجرای متوالی روی همان مشتری محلی با ۳۱ محصول:

| پاسخ JSON بدون فشرده‌سازی | تعداد محصول | بایت |
|---|---:|---:|
| list قدیمی با limit=500 | ۳۱ | ۴۸٬۲۱۶ |
| بخش اول جدید | ۲۴ | ۲۳٬۸۵۲ |
| ادامهٔ جدید | ۷ | ۷٬۴۳۸ |
| مجموع کاتالوگ جدید، دو درخواست | ۳۱ یکتا | ۳۱٬۲۹۰ |

زمان همان نمونه: list قدیمی ۳۰۳ms و بخش اول جدید ۱۹۹ms. این اندازه‌گیری تک‌نمونه‌ای محلی، benchmark و تضمین latency پروداکشن نیست؛ session/facets، تصاویر، فایل‌های برنامه و هزینهٔ کل مرورگر را شامل نمی‌شود.

## حدود و انتشار

- کش فقط در حافظهٔ اجرای جاری است؛ بستن برنامه باعث بارگیری مجدد می‌شود. تصاویر کامل کاتالوگ پیشاپیش دانلود نمی‌شوند.
- اندازهٔ واقعی کاتالوگ مشتریان، heap و long-task مرورگر در پروداکشن و شمارش runtime همهٔ خواندن‌های API→CMS `[UNKNOWN]` است. کاهش payload نمونه یا پاس‌شدن fixture، اثبات ظرفیت همهٔ دستگاه‌ها نیست.
- بازخوانی کامل به‌جای delta انجام می‌شود و ممکن است نسبت به بارگیری صرفاً بر اساس اسکرول، مصرف انتقال بیشتری داشته باشد؛ stale شدن به‌تنهایی شبکه ایجاد نمی‌کند.
- مهاجرت داده و وابستگی جدیدی برای قابلیت کاتالوگ اضافه نشده است. PostgreSQL مبنای endpointهای جدید browse است.
- انتشار پروداکشن، push یا deploy انجام نشده است. ترتیب انتشار: CMS دارای endpointهای داخلی، API جدید، سپس SPA. برای rollback SPA، APIهای قدیمی را تا پایان دورهٔ سازگاری نگه دارید.
