# گزارش جامع ممیزی امنیتی و بدهی‌های فنی — PersianPart 2.0 (OWASP Top 10)

**محیط ممیزی:** `PersianPart 2.0` (شامل `apps/api`, `apps/cms`, `apps/web`, `packages/contract`)  
**تاریخ ارزیابی:** ۱۰ نوامبر ۲۰۲۶  
**مرجع استاندارد:** OWASP Top 10 (2021/2025 Standard) & NIST SP 800-63B  
**نقش عامل:** کاوشگر ممیزی امنیت و معماری سیستم (Security & OWASP Top 10 Auditor Explorer)

---

## چکیده مدیریتی (Executive Summary)

پروژه **PersianPart 2.0** به عنوان یک پلتفرم تجارت الکترونیک B2B قطعات، از معماری مدرن بر پایه Monorepo (شامل Hono بر بستر Bun در `apps/api`، سامانه مدیریت محتوای Payload CMS v3 بر بستر Next.js و PostgreSQL در `apps/cms`، کلاینت SPA با Vite و React 19 در `apps/web`، و قرارداد یکپارچه oRPC v2 در `packages/contract`) بهره می‌برد.

در تحلیل عمیق کد منبع و رفتار سیستم برای سناریوی **چندین هزار کاربر فعال همزمان**، نقاط قوت ساختاری متعددی نظیر استفاده از قفل‌های ردیفی پایگاه داده (`FOR UPDATE` و `FOR SHARE`) در ثبت سفارش و مدیریت تراکنش انبار مشاهده شد. با این حال، **آسیب‌پذیری‌های امنیتی بحرانی (Critical) و با ریسک بالا (High)** شناسایی شدند که پیش از استقرار در محیط عملیاتی با بار بالا باید مرتفع گردند:
1. **پیکربندی خطرناک CORS با بازتاب پویای مبدا (Dynamic Origin Reflection) به همراه اعتبارنامه‌ها (`credentials: true`)** که امکان سرقت اطلاعات کاربر را از طریق وب‌سایت‌های مخرب فراهم می‌کند.
2. **افشای عمومی مدارک احراز هویت و صنفی مشتریان (KYC Leakage)** به دلیل ذخیره‌سازی مدارک پروانه کسب و شناسنامه در مجموعه رسانه‌ای عمومی (`media`) با دسترسی `read: () => true` و توزیع عمومی از طریق CDN.
3. **کلیدهای سخت‌کد شده و نشت کلید API سرویس پیامک کاوه‌نگار** در فایل منبع و ثبت شماره همراه مشتریان به همراه کلید در لاگ‌های سیستمی.
4. **ذخیره‌سازی متن‌باز (Plaintext) کدهای OTP در دیتابیس** و امکان مشاهده کدهای ورود کاربران توسط مدیران ارشد در پنل CMS.
5. **نبود مکانیزم Rate Limiting مبتنی بر IP در ارسال OTP** که سامانه را در برابر حملات SMS Bombing و تحمیل هزینه‌های سنگین مالی آسیب‌پذیر می‌کند.
6. **مبتنی بر حافظه بودن باطل‌سازی توکن‌ها (In-Memory Token Revocation)** و طول عمر ۳۰ روزه توکن‌های JWT بدون امکان مقیاس‌پذیری افقی (Horizontal Scaling).
7. **پیاده‌سازی ماک/استاب اعتبارسنجی درگاه پرداخت (`verifyPayment`)** بدون اعتبارسنجی امضای شاپرک/بانک.

## بخش ۱: ممیزی تفصیلی بر اساس OWASP Top 10

### A01:2021 – Broken Access Control (شکست در کنترل دسترسی)

#### ۱.۱. دسترسی عمومی به مدارک هویتی و پروانه‌های کسب مشتریان (Severity: CRITICAL)
- **موقعیت کد:**
  - `apps/cms/src/collections/users/users.collection.ts` (سطرهای ۴۴۴ تا ۴۵۱)
  - `apps/cms/src/collections/media/media.collection.ts` (سطر ۲۲)
  - `apps/api/src/server.ts` (سطرهای ۱۵۹ تا ۱۹۷)
  - `docker-compose.yml` (سطرهای ۱۳۴ تا ۱۳۷)
- **مشاهده عینی:**
  در کالکشن `users`، فیلد آپلود مدارک صنفی خریداران (`business_license`, `nationalCode`, `operating_license`) به کالکشن `media` ارجاع داده شده است:
  ```ts
  // apps/cms/src/collections/users/users.collection.ts:444
  name: "file",
  type: "upload",
  relationTo: "media",
  required: true,
  label: "فایل مدرک (تصویر)",
  ```
  در حالی که در تعریف کالکشن `media`:
  ```ts
  // apps/cms/src/collections/media/media.collection.ts:22
  access: {
    read: () => true,
    create: isCatalogManager,
  ...
  ```
  همچنین در سرور API مسیر `/api/media/*` بدون نیاز به هیچ احراز هویتی فایل‌ها را برمی‌گرداند (`Access-Control-Allow-Origin: *`) و کانتینر NGINX CDN نیز پوشه `/data` را به طور عمومی با `NGINX_CORS_ORIGIN: "*"` سرو می‌کند.
- **تحلیل آسیب‌پذیری و پیامد:**
  مدارک محرمانه هویتی و اسناد کسب‌وکار خریداران B2B در همان محلی ذخیره می‌شوند که تصاویر عمومی محصولات کاتالوگ قرار دارند. هر کاربری با حدس زدن یا استخراج نام فایل (مانند `license.jpg` یا شناسه ترتیبی) می‌تواند بدون احراز هویت اسناد رسمی مشتریان دیگر را دانلود کند (نقص فاحش حریم خصوصی و نقض الزامات GDPR/قوانین داده‌های شخصی).
- **راهکار اصلاحی:**
  ایجاد یک کالکشن مجزا به نام `documents` یا `kyc-media` با دسترسی `read` محدود: `({ req }) => isSalesManager({ req }) || { 'user.id': { equals: req.user.id } }` و سرو نشدن این فایل‌ها از طریق CDN یا مسیرهای عمومی رسانه.

#### ۱.۲. بای‌پس سطح دسترسی فیلدها از طریق Master API Key در API Backend (Severity: HIGH)
- **موقعیت کد:**
  - `apps/cms/src/sdk.ts` (سطرهای ۱۵۷ تا ۱۶۳)
  - `apps/api/src/server.ts` (سطر ۱۱۵)
- **مشاهده عینی:**
  سرور Hono در `apps/api` تمام ارتباطات خود با Payload CMS را با استفاده از یک API Key واحد در سطح ادمین برقرار می‌کند:
  ```ts
  // apps/cms/src/sdk.ts:157
  if (options.apiKey || (typeof process !== 'undefined' && process.env?.CMS_API_KEY)) {
    const key = options.apiKey || process.env.CMS_API_KEY
    baseHeaders['Authorization'] = `admins API-Key ${key}`
  }
  ```
- **تحلیل آسیب‌پذیری و پیامد:**
  در این معماری، قوانین دسترسی داخلی Payload CMS (`access.read`, `access.update` و ...) برای هیچ‌یک از درخواست‌های API اجرا نمی‌شوند؛ زیرا SDK همیشه در نقش Superadmin/Service عمل می‌کند. کل امنیت داده‌ها به دقت نویسنده در روت‌های `apps/api/src/routers` متکی است. چنانچه در هر روتی فیلتر `where: { user: { equals: context.user.id } }` فراموش شود، کل داده‌های کاربران دیگر فاش خواهد شد (IDOR با بالاترین سطح دسترسی).
- **راهکار اصلاحی:**
  استفاده از رویکرد Impersonation یا انتقال توکن کاربر جاری (`Authorization: Bearer ${userToken}`) در درخواست‌های SDK از Payload CMS به گونه‌ای که دسترسی‌های سطح کاربر درون هسته CMS نیز ارزیابی گردند.

#### ۱.۳. نشت یادداشت‌های داخلی کارشناسان فروش در خروجی سفارش مشتری (Severity: MEDIUM)
- **موقعیت کد:**
  - `apps/cms/src/collections/orders/orders.collection.ts` (سطرهای ۲۰۸ تا ۲۱۴)
  - `apps/api/src/routers/router.helpers.ts` (سطرهای ۲۴۱ تا ۲۶۴)
  - `packages/contract/src/order.ts` (سطر ۱۶۸)
- **مشاهده عینی:**
  فیلد `notes` در مدل سفارش به صورت «یادداشت داخلی - هماهنگی‌ها و توضیحات داخلی کارشناسان فروش» تعریف شده است. در تابع `sanitizeOrderForCustomer`:
  ```ts
  // apps/api/src/routers/router.helpers.ts:243
  const sanitized = { ...order, orderNumber: String(order.trackingNumber ?? order.orderNumber) }
  ```
  فیلد `notes` حذف نمی‌شود و در `CustomerOrderDocumentSchema` نیز مجاز شمرده شده است.
- **تحلیل آسیب‌پذیری و پیامد:**
  اگر کارشناسان فروش در پنل CMS یادداشت‌های داخلی درباره حاشیه سود، اعتبار مشتری یا نکات اختصاصی ثبت کنند، این اطلاعات مستقیماً در پاسخ API جزئیات سفارش به خریدار نمایش داده می‌شود.
- **راهکار اصلاحی:**
  تفکیک فیلد به `internalNotes` (فقط ادمین) و `customerNotes` یا حذف صریح فیلد `notes` در `sanitizeOrderForCustomer`.

### A02:2021 – Cryptographic Failures (شکست‌های رمزنگاری)

#### ۲.۱. کلید وب‌سرویس پیامک کاوه‌نگار سخت‌کد شده در سورس کد (Severity: CRITICAL)
- **موقعیت کد:**
  - `apps/api/src/lib/kavenegar.ts` (سطرهای ۳۵ تا ۳۶)
  - `docker-compose.yml` (سطر ۴۱)
- **مشاهده عینی:**
  ```ts
  // apps/api/src/lib/kavenegar.ts:35
  const DEFAULT_API_KEY =
    '46437751615871547A59364B75376339706E72384266734A596F3476644B653641356171462F557A5747383D'
  ```
- **تحلیل آسیب‌پذیری و پیامد:**
  یک کلید عملیاتی API سرویس کاوه‌نگار مستقیماً در متن کد ریپازیتوری کامیت شده است. هر فردی با دسترسی به کد می‌تواند با استفاده از این کلید اقدام به ارسال پیامک انبوه، تخلیه موجودی ریالی حساب، استراق سمع پیامک‌های دریافتی، یا اختلال در سرویس OTP شرکت نماید.
- **راهکار اصلاحی:**
  کلید فوق بلافاصله در پنل کاوه‌نگار باطل (Revoke) شده و کلید جدید صرفاً از طریق Secrets Manager یا متغیرهای محیطی امن بدون مقدار پیش‌فرض تزریق گردد.

#### ۲.۲. ذخیره کدهای یکبار مصرف (OTP) به صورت Plaintext در دیتابیس (Severity: HIGH)
- **موقعیت کد:**
  - `apps/api/src/lib/otp.ts` (سطر ۷۳ و ۸۷)
  - `apps/cms/src/collections/otps/otps.collection.ts` (سطرهای ۱۸ تا ۲۱ و ۶۰ تا ۶۷)
- **مشاهده عینی:**
  ```ts
  // apps/api/src/lib/otp.ts:73
  data: {
    code,
    expiresAt,
    cooldownUntil,
    attempts: 0,
    user: userId,
  }
  ```
  و در تعریف کالکشن CMS:
  ```ts
  // apps/cms/src/collections/otps/otps.collection.ts:18
  access: {
    read: ({ req }) => isSuperAdmin({ req }) || isServiceAdmin({ req }),
  ...
  name: 'code',
  type: 'text',
  label: 'کد تایید فعال',
  ```
- **تحلیل آسیب‌پذیری و پیامد:**
  کدهای تایید ۴ رقمی به صورت متن آشکار ذخیره می‌شوند. هرگونه نشت بک‌آپ پایگاه داده یا دسترسی یک حساب سوپرادمین به پنل، امکان مشاهده کد فعال تمام مشتریان و سرقت هویت آن‌ها (Session Hijacking) بدون دسترسی به موبایل مشتری را فراهم می‌کند.
- **راهکار اصلاحی:**
  کد OTP باید قبل از ذخیره در دیتابیس با یک Salt امن هش شود (مانند `crypto.createHash('sha256').update(phone + code + salt).digest('hex')`) و هنگام ارزیابی، هش ورودی کاربر با هش ذخیره‌شده مقایسه گردد. فیلد `code` نیز باید در ادمین پنل `hidden: true` باشد.

#### ۲.۳. انتروپی پایین کد تایید (۴ رقم عددی) (Severity: MEDIUM)
- **موقعیت کد:**
  - `apps/api/src/lib/otp.ts` (سطرهای ۳۳ تا ۳۵)
- **مشاهده عینی:**
  ```ts
  export function generateRandomCode(): string {
    return String(crypto.randomInt(1000, 10000))
  }
  ```
- **تحلیل آسیب‌پذیری و پیامد:**
  تعداد کل حالت‌های ممکن فقط ۹,۰۰۰ حالت است (تقریباً ۱۳ بیت انتروپی). مطابق استاندارد NIST SP 800-63B و OWASP ASVS، کدهای احراز هویت باید حداقل ۶ رقم (۱,۰۰۰,۰۰۰ حالت) باشند تا ریسک حدس زدن تصادفی در بازه ۲ دقیقه‌ای کاهش یابد.
- **راهکار اصلاحی:**
  ارتقای تولید کد به ۶ رقم: `crypto.randomInt(100000, 1000000)`.

#### ۲.۴. کلیدهای پشتیبان (Fallback) پیش‌فرض توسعه در محیط‌های مختلف (Severity: HIGH)
- **موقعیت کد:**
  - `apps/api/src/lib/jwt.ts` (سطر ۴)
  - `apps/api/src/server.ts` (سطر ۱۱۵)
  - `apps/api/src/routers/activity-feed.ts` (سطر ۲۰)
  - `apps/cms/src/payload.config.ts` (سطر ۱۴۳)
- **مشاهده عینی:**
  کلیدهای پیش‌فرض نظیر `'persianpart_dev_api_key_2026'` و `'persianpart-dev-secret-key-32-chars-long!!'` در صورت تنظیم نبودن متغیر محیطی یا زمانی که `NODE_ENV` دقیقاً برابر `'production'` نباشد (مانند محیط‌های Staging یا CI) فعال می‌شوند.
- **راهکار اصلاحی:**
  حذف کلیه Fallbackهای متنی؛ برنامه در صورت فقدان متغیر محیطی باید با خطای Fatal بلافاصله متوقف شود (Fail-Fast).

### A03:2021 – Injection (تزریق)

#### ۳.۱. امکان آپلود فایل‌های SVG و پتانسیل حمله Stored XSS (Severity: HIGH)
- **موقعیت کد:**
  - `apps/api/src/server.ts` (سطرهای ۱۰۹ تا ۱۱۱ و ۱۷۴ تا ۱۷۹)
- **مشاهده عینی:**
  در هندلر آپلود فایل رسانه:
  ```ts
  // apps/api/src/server.ts:109
  const safeExts = ['.jpg', '.jpeg', '.png', '.webp', '.svg', '.gif', '.avif', '.pdf']
  ```
  پسوند `.svg` در لیست پسوندهای مجاز قرار داده شده است. فایل‌های آپلود شده سپس با همان نوع محتوا توسط Hono سرو می‌شوند:
  ```ts
  // apps/api/src/server.ts:178
  'Content-Type': file.type || 'application/octet-stream',
  ```
- **تحلیل آسیب‌پذیری و پیامد:**
  فایل‌های SVG مبتنی بر XML هستند و می‌توانند حاوی تگ‌های `<script>` یا رویدادهای جاوااسکریپت (مانند `onload`) باشند. در صورتی که کاربری یک SVG مخرب آپلود کند و کاربر یا مدیر دیگری آن فایل را از طریق آدرس API باز کند، اسکریپت در مبدا (Origin) سایت اجرا شده و می‌تواند به توکن‌ها و کوکی‌ها دسترسی پیدا کند (Stored Cross-Site Scripting).
- **راهکار اصلاحی:**
  1. حذف `.svg` از لیست آپلود، یا
  2. استفاده از پکیج‌های پاک‌سازی SVG مانند `DOMPurify` / `is-svg`، یا
  3. سرو کردن فایل‌های SVG فقط با هدر `Content-Disposition: attachment` و هدر `Content-Security-Policy: default-src 'none'`.

#### ۳.۲. ارزیابی تزریق SQL (SQL Injection) در کوئری‌های خام (Severity: LOW / SECURE)
- **موقعیت کد:**
  - `apps/cms/src/endpoints/catalog-browse.endpoint.ts` (سطرهای ۱۳ تا ۳۶)
  - `apps/cms/src/endpoints/activity-feed.endpoint.ts` (سطرهای ۱۴۳ تا ۱۹۰)
- **مشاهده عینی:**
  در اندپوینت‌های فوق، کوئری‌های خام SQL مستقیماً به استخر اتصالات (`pool.query`) ارسال می‌شوند. ارزیابی دقیق نشان داد که تمام ورودی‌ها از طریق آرایه پارامترهای پیوند داده شده (`$1`, `$2`, ...) تزریق می‌شوند و کاراکترهای ویژه جستجو مانند `%` و `_` نیز به صورت دستی Escape شده‌اند:
  ```ts
  const pattern = param(`%${input.search.trim().toLowerCase().replace(/[\\%_]/g, '\\$&')}%`)
  ```
- **نتیجه‌گیری:** مکانیزم‌های استفاده‌شده در برابر SQL Injection ایمن هستند.

### A04:2021 – Insecure Design (طراحی ناامن و آسیب‌پذیری‌های منطق کسب‌وکار)

#### ۴.۱. اعتبارسنجی ماک/جعلی درگاه پرداخت (Severity: HIGH)
- **موقعیت کد:**
  - `apps/api/src/routers/shopping.ts` (سطرهای ۱۴۲ تا ۱۶۶)
- **مشاهده عینی:**
  ```ts
  const verifyPayment = authed.shopping.verifyPayment.handler(async ({ input, context, errors }) => {
    if (!input?.orderId) {
      throw errors.BAD_REQUEST({ message: 'شناسه سفارش نامعتبر است.' })
    }
    const orderDoc: any = await findOrderByIdOrNumber(input.orderId, 1)
    if (!orderDoc) {
      throw errors.NOT_FOUND({ message: 'سفارش مورد نظر یافت نشد.' })
    }
    // بررسی مالکیت سفارش...
    return {
      verified: true,
      message: 'سفارش معتبر و در حال پردازش است.',
      orderId: input.orderId,
    }
  })
  ```
- **تحلیل آسیب‌پذیری و پیامد:**
  پروسه تایید تراکنش بانکی هیچ امضا، توکن پیگیری، استعلام شاپرک یا اعتبارسنجی مبلغ از وب‌سرویس درگاه ندارد. هر کاربری پس از ایجاد سفارش، با فراخوانی این متد وضعیت تایید دریافت می‌کند. اگر در آینده منطق انتقال وضعیت سفارش بر پایه این متد قرار گیرد، امکان ثبت سفارش پرداخت‌شده بدون پرداخت ریالی وجود خواهد داشت.
- **راهکار اصلاحی:**
  پیاده‌سازی یکپارچه ماژول پرداخت بر اساس استاندارد درگاه‌های پرداخت شاپرکی (کال‌بک رسمی، اعتبارسنجی امضای دیجیتال، متد `verify` دو مرحله‌ای و کنترل عدم تکرار شماره تراکنش RRN/RefNum).

#### ۴.۲. شرایط رقابتی (TOCTOU Race Condition) در شمارنده تلاش‌های OTP (Severity: MEDIUM)
- **موقعیت کد:**
  - `apps/api/src/lib/otp.ts` (سطرهای ۱۰۴ تا ۱۸۲)
- **مشاهده عینی:**
  در متد `verifyOtp`، رکورد ابتدا با `sdk.find` خوانده می‌شود، سپس تعداد `record.attempts` در حافظه جاوااسکریپت بررسی و در صورت اشتباه بودن کد با `sdk.update` ذخیره می‌گردد. هیچ قفل ردیفی یا عملیات اتمیک پایگاه‌داده وجود ندارد.
- **تحلیل آسیب‌پذیری و پیامد:**
  یک مهاجم با ارسال همزمان (Concurrent) ده‌ها درخواست حدس کد در بازه چند میلی‌ثانیه می‌تواند از محدودیت `MAX_ATTEMPTS = 5` عبور کرده و تعداد تلاش‌های بسیار بیشتری انجام دهد؛ زیرا تمام درخواست‌ها قبل از ثبت آپدیت اول، تعداد تلاش را ۰ یا ۱ می‌خوانند.
- **راهکار اصلاحی:**
  افزایش تعداد تلاش به صورت اتمیک در SQL:
  `UPDATE otps SET attempts = attempts + 1 WHERE phone = $1 RETURNING attempts`.

#### ۴.۳. مقیاس‌پذیری و گلوگاه Double HTTP Hop تحت بار بالا (Severity: HIGH)
- **موقعیت کد:**
  - سرتاسر `apps/api`
- **مشاهده عینی:**
  هر عملیاتی در `apps/api` (که روی پورت ۵۱۷۵ اجرا می‌شود) برای دریافت اطلاعات از Payload CMS (روی پورت ۵۱۷۴) یک درخواست شبکه HTTP با فرمت JSON ارسال می‌کند و سپس Payload CMS به دیتابیس متصل می‌شود.
- **تحلیل آسیب‌پذیری و معماری:**
  در بار ترافیکی چند هزار کاربر همزمان، این معماری با ۲ برابر شدن تعداد درخواست‌های شبکه داخلی، تاخیر مضاعف (Network Latency)، مصرف CPU بالا در Serialize/Deserialize مداوم JSON، و اتمام پورت‌های محلی (Socket/Port Exhaustion) مواجه خواهد شد.
- **راهکار اصلاحی:**

### A05:2021 – Security Misconfiguration (پیکربندی نادرست امنیتی)

#### ۵.۱. فاجعه پیکربندی CORS: بازتاب پویا همراه با Allow-Credentials (Severity: CRITICAL)
- **موقعیت کد:**
  - `apps/api/src/server.ts` (سطرهای ۴۱ تا ۴۹)
  - `docker-compose.yml` (سطر ۴۰)
- **مشاهده عینی:**
  ```ts
  // apps/api/src/server.ts:41
  app.use(
    '*',
    cors({
      origin: (origin) => origin || '*',
      allowMethods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
      allowHeaders: ['Content-Type', 'Authorization', 'X-Requested-With'],
      credentials: true,
      maxAge: 86400,
    })
  )
  ```
- **تحلیل آسیب‌پذیری و پیامد:**
  این آسیب‌پذیری یکی از خطرناک‌ترین خطاهای CORS در استاندارد OWASP است. بازگرداندن مقدار هدر `Origin` ورودی کلاینت به عنوان `Access-Control-Allow-Origin` همراه با `Access-Control-Allow-Credentials: true` به این معناست که **هر وب‌سایت در اینترنت** (مانند `https://evil-attacker.com`) می‌تواند از طرف کاربری که وارد سایت شده، به API درخواست زده و تمام پاسخ‌ها شامل اطلاعات حساب، آدرس‌ها، سفارش‌ها و اطلاعات هویتی را بخواند! متغیر محیطی `CORS_ORIGINS` در داکر تعریف شده ولی در کد کاملاً نادیده گرفته شده است.
- **راهکار اصلاحی:**
  جایگزینی تابع مبدا با اعتبارسنجی بر اساس لیست سفید دقیق:
  ```ts
  const allowedOrigins = (process.env.CORS_ORIGINS || '').split(',').map(s => s.trim()).filter(Boolean)
  app.use('*', cors({
    origin: (origin) => allowedOrigins.includes(origin) ? origin : null,
    credentials: true,
  }))
  ```

#### ۵.۲. فقدان کامل هدرهای امنیتی در تمام سرویس‌ها (Severity: HIGH)
- **موقعیت کد:**
  - `apps/api/src/server.ts`
  - `apps/cms/next.config.ts`
- **مشاهده عینی:**
  در هیچ‌یک از سرویس‌های API و CMS هدرهای امنیتی استاندارد اعمال نشده‌اند:
  - عدم وجود `Strict-Transport-Security` (HSTS)
  - عدم وجود `Content-Security-Policy` (CSP)
  - عدم وجود `X-Frame-Options: DENY` یا `SAMEORIGIN` (آسیب‌پذیری Clickjacking در پنل مدیریت)
  - عدم وجود `X-Content-Type-Options: nosniff` (خطر MIME Sniffing)
  - عدم وجود `Referrer-Policy: strict-origin-when-cross-origin`
- **راهکار اصلاحی:**
  افزودن میدلور `secureHeaders()` در Hono (`apps/api`) و تنظیم هدرهای امنیتی در کانفیگ Next.js (`apps/cms`).

#### ۵.۳. نشت جزئیات خطاهای داخلی سیستم در پاسخ‌های ۵۰۰ (Severity: MEDIUM)

- **تحلیل آسیب‌پذیری و پیامد:**
  متن کامل خطاهای داخلی سیستم (مانند پیام‌های خطای پایگاه داده، مسیرهای فایل روی سرور یا خطاهای پکیج‌ها) در کلاینت منعکس می‌شود که ابزار مفیدی برای شناسایی ساختار داخلی توسط مهاجمین است.

### A10:2021 – Server-Side Request Forgery (SSRF) (جعل درخواست سمت سرور)

#### ۱۰.۱. پراکسی فوروارد باز `/api/openapi/*` و خطر دسترسی به روت‌های داخلی CMS (Severity: MEDIUM)

- **تحلیل آسیب‌پذیری و پیامد:**

- **راهکار اصلاحی:**

### ۲.۲. موازنه‌های فنی و معماری (Architectural Trade-offs)

در فرآیند توسعه فعلی PersianPart 2.0، چندین موازنه آگاهانه یا مصلحتی بین سرعت توسعه و الزامات سخت‌گیرانه تولید اتخاذ شده است:

1. **سرعت توسعه در برابر اصل کمترین دسترسی (Zero-Trust vs Developer Velocity):**
   - *تصمیم اتخاذ شده:* استفاده از یک کلید سراسری ادمین (`CMS_API_KEY`) برای تمام فراخوانی‌های `apps/api` به Payload CMS.
   - *مزیت حاصله:* توسعه بسیار سریع روت‌ها و رهایی از پیچیدگی‌های احراز هویت تو در تو در هر درخواست بین دو اپلیکیشن.
   - *هزینه/ریسک متقبل شده:* لغو کامل گیت‌های امنیتی پیش‌فرض Payload CMS و انتقال ۱۰۰٪ مسئولیت اعتبارسنجی به کدهای سرور Hono.
2. **پایداری بدون وابستگی خارجی در برابر مقیاس‌پذیری افقی (Stateless Simplicity vs Scalability):**
   - *تصمیم اتخاذ شده:* پیاده‌سازی انبار توکن‌های لغو شده به صورت `Map` درون حافظه Bun بدون استقرار سرور Redis.
   - *مزیت حاصله:* راه‌اندازی سریع پروژه روی سرورهای آزمایشی تنها با یک دیتابیس PostgreSQL بدون نیاز به نگهداری کلاستر کش.
   - *هزینه/ریسک متقبل شده:* ناتوانی در اجرای بیش از یک نمونه (Instance) از کانتینر API؛ با ری‌استارت شدن کانتینر توکن‌های خروج یافته مجدداً احیا می‌شوند.
3. **تجربه کاربری ثبت‌نام اختصاصی در برابر جلوگیری از سرشماری هویت (UX vs Anti-Enumeration):**
   - *تصمیم اتخاذ شده:* اعلام صریح اینکه «شماره در سیستم تعریف نشده است و باید با مدیریت تماس بگیرید».
   - *مزیت حاصله:* راهنمایی فوری خریدار جدید که این سامانه یک پرتال B2B بسته است و او باید جهت مدارک هماهنگ کند.
   - *هزینه/ریسک متقبل شده:* افشای وضعیت ثبت بودن یا نبودن شماره تلفن‌ها در پایگاه داده پرشین پارت برای ابزارهای اسکرپر خارجی.
4. **سادگی مدیریت فایل‌ها در برابر محرمانگی چندسطحی (Unified Media vs Multi-Vault Storage):**
   - *تصمیم اتخاذ شده:* بارگذاری تصاویر محصول، لوگوها، کاتالوگ‌ها و اسناد هویتی خریداران همگی در یک کالکشن `media` که در پوشه مشترک `/app/media` مونت می‌شود.
   - *مزیت حاصله:* ساده ماندن تنظیمات NGINX و کد آپلود فرانت‌اند.
   - *هزینه/ریسک متقبل شده:* افشای اسناد محرمانه مشتریان روی CDN عمومی با CORS ستاره (`*`).

## بخش ۳: برنامه عملیاتی اصلاحات امنیتی (Remediation Roadmap)

جهت ایمن‌سازی کامل سامانه برای پوشش سناریوی چندهزار کاربر فعال، اقدامات به ترتیب اولویت زمانی دسته‌بندی می‌شوند:

### فاز ۱: اصلاحات فوری و اضطراری (Hotfixes - قبل از بازگشایی ترافیک)
1. **اصلاح فاجعه CORS در `apps/api/src/server.ts`:**
   - استفاده انحصاری از لیست سفید دامنه‌ها بر اساس `process.env.CORS_ORIGINS`.
2. **باطل‌سازی کلید افشا شده کاوه‌نگار و امن‌سازی لاگ‌ها:**
   - تغییر کلید در پنل کاوه‌نگار و حذف مسیر URL کامل از لاگ‌های خطای `apps/api/src/lib/kavenegar.ts`.
3. **محدودسازی دسترسی به اسناد KYC:**
   - مسدود کردن دسترسی مستقیم عمومی به تصاویر اسناد کاربران در NGINX CDN و جداسازی کالکشن اسناد از رسانه‌های عمومی کاتالوگ.
4. **حذف فرمت `.svg` از لیست پسوندهای مجاز آپلود:**
   - در `apps/api/src/server.ts` سطر ۱۰۹ پسوند `.svg` حذف شود تا از ریسک حملات Stored XSS جلوگیری گردد.

### فاز ۲: مقاوم‌سازی لایه احراز هویت و داده‌ها (Hardening)
1. **استقرار لایه کشینگ و سشن Redis:**
   - انتقال ذخیره بلک‌لیست توکن‌های منقضی (`revokedTokens`) به Redis.
   - افزودن Rate Limiter توزیع‌شده بر پایه IP و شماره تلفن برای جلوگیری از SMS Bombing.
2. **هش‌سازی کدهای OTP در دیتابیس:**
   - ذخیره هش SHA-256 کد OTP در جدول به جای متن ساده و تغییر طول کد به ۶ رقم عددی.
3. **اصلاح خروجی متدها در قرارداد (Contract Sanitization):**
   - حذف کامل `z.any()` از خروجی‌های سفارش و کاتالوگ در `packages/contract`.
   - حذف فیلد `notes` در `sanitizeOrderForCustomer`.

### فاز ۳: معماری مقیاس‌پذیر و درگاه پرداخت رسمی (Scalability & Integrations)
1. **اتصال واقعی به سرویس پرداخت الکترونیک شاپرک:**
   - جایگزینی لاجیک تایید پرداخت با استعلام وب‌سرویس و اعتبارسنجی ارقام تراکنش.
2. **حذف Double HTTP Hop در API:**
   - بازنویسی دسترسی‌های پرکاربرد (مانند استعلام کاتالوگ و احراز هویت اولیه) به صورت کوئری مستقیم پایگاه داده درون API جهت کاهش Latency به کمتر از ۱۰ میلی‌ثانیه.
3. **افزودن هدرهای محافظتی وب:**
   - فعال‌سازی `secureHeaders` در Hono و هدرهای امنیتی در کانفیگ سرور NGINX و Next.js.
