# طراحی «طرح» (خانوادهٔ محصول) — نسخهٔ ساده‌شده

تاریخ: ۲۰۲۶-۱۱-۲۱ — مبنای مخزن: `52219a4`

این سند جایگزین `.agents/brain/product-families-implementation-plan.md` است. هرجا تعارض داشتند، این سند معتبر است. بخش‌هایی از پلن قبلی که اینجا «بدون تغییر» آمده‌اند، با همان جزئیات پلن قبلی اجرا می‌شوند.

## ۱. نیاز و چرایی

یک کارخانه طرحی مثل «آلاوس» (پرسپولیس یزد) را در چند درجه (۱، ۲، ۳، D)، چند ابعاد (۱۲۰×۲۸۰، ۱۲۰×۱۲۰)، چند رنگ (طوسی روشن/تیره) و چند لعاب (مات/پولیش) تولید می‌کند. ما هر ترکیب را یک کالای مستقل با SKU، قیمت، موجودی و سفارش خودش نگه می‌داریم. ولی مشتری باید از هر کالا بقیهٔ نسخه‌های همان طرح را ببیند و با یک کلیک به آن‌ها برود.

«طرح» در این سند همان «خانوادهٔ محصول» است. نام کالا طبق `docs/11` برابر «طرح + رنگ + لعاب» است و درجه و ابعاد فیلدهای جدا هستند. پس نام عضو همراه با درجه و ابعاد برای تمایز اعضا کافی است.

اقدام فوری بعد از انتشار: مدیر کالاهای فعلی را یکجا گروه‌بندی می‌کند. بعد از آن، هر کالای جدید هنگام ثبت به طرحش وصل می‌شود.

## ۲. اهداف، غیراهداف، ضداهداف

**اهداف**
- رابطهٔ دستی و اختیاری کالا ← طرح، حداکثر یک طرح برای هر کالا.
- بخش «گزینه‌های دیگر این محصول» در مودال Web و صفحهٔ محصول Catalog عمومی.
- گروه‌بندی اولیهٔ سریع با ابزار بومی ادمین.

**غیراهداف** (بدون تغییر نسبت به پلن قبلی، §۱ «خارج از دامنه»)
- variant، ارث‌بری، صفحه یا فیلتر یا جست‌وجوی خانواده و تغییر URL را نداریم.
- فیلد تازهٔ لعاب، ترتیب دستی و محصول پیش‌فرض اضافه نمی‌شود.
- داده‌های واقعی گروه‌بندی یا اصلاح نمی‌شوند و backfill خودکار هم نداریم.
- **ثبت collection جدید در MCP** در این نسخه انجام نمی‌شود.

**ضداهداف**: هرکدام از این‌ها رخ دهد، کار شکست خورده است، حتی اگر کار کند.
- گزینه‌ای که کاربر Web به آن دسترسی ندارد، یا عضوی که در Catalog منتشر نشده، دیده شود.
- قیمت یا موجودی مخفی از طریق گزینه‌ها نشت کند.
- انتخاب یک گزینه، سبد یا انتخاب خرید را تغییر دهد.

## ۴. طراحی

### ۴.۱ CMS: مدل داده و ادمین

**بدون تغییر نسبت به پلن قبلی، §۳**، به‌جز این موارد:

- **برچسب‌ها:** مفرد/جمع «طرح» / «طرح‌ها». slug همچنان `product-families` و فیلد روی محصول همچنان `family`. نام پیشنهادی هر طرح: «آلاوس — پرسپولیس یزد».
- **توضیح فیلد روی محصول:** «طرحی که این کالا یکی از نسخه‌های آن است. تغییر این فیلد فقط همین کالا را جابه‌جا می‌کند.»
- **گروه‌بندی اولیه:** با Edit many بومی لیست محصولات: فیلتر نام/برند، انتخاب همه، تنظیم `family`. این مسیر باید روی ادمین محلی مشاهده شود: آیا Edit many فیلد relationship را نشان می‌دهد و ساخت طرح تازه از داخل آن ممکن است؟ اگر نشد، در گزارش ثبت شود. ابزار سفارشی ساخته نمی‌شود.
- **MCP:** حذف از دامنه (§۲). schema محصول در MCP اگر خودکار از collection مشتق می‌شود، رابطهٔ جدید را منعکس می‌کند. guard یا مجوزی تغییر نمی‌کند.
- **باقی موارد:** collection، Join، ACL، `protectBusinessRelations` با `referenceActions`، FK با `ON DELETE RESTRICT`، migration افزایشی، تایپ‌های generated، لاگ `product_update` و rehearsal محلی همگی طبق پلن قبلی‌اند.

### ۴.۲ قرارداد و API برای Web

- به `CatalogRecordSchema` فیلد `familyId: number | null | undefined` اضافه می‌شود: integer مثبت و optional برای snapshotهای قدیمی. خروجی جدید سرور همیشه عدد یا null است.
- `productProjection` در `apps/api/src/routers/catalog-sync.ts` شامل `family` می‌شود. `catalogRecord` مقدار رابطه را، چه عدد و چه آبجکت populated، به شناسه تبدیل می‌کند و آبجکت خام رابطه را به مرورگر نمی‌فرستد. چون `depth: 1` است، populate شدن خانواده باید بررسی شود: یا `family` را به شناسه نرمال کن، یا با `maxDepth: 0` روی فیلد جلوی populate را بگیر.
- همهٔ مسیرهای موجود (`syncPage`، `getByIds`، `browse`، خواندن تکی و scan) از همین `catalogRecord` استفاده می‌کنند و چیز دیگری لازم نیست.
- **procedure، handler یا router جدیدی ساخته نمی‌شود.**

### ۴.۳ Web: داده

- تایپ `Product` در Web تغییر نمی‌کند. `familyId` مستقیم از رکورد خام `byId[product.id]` خوانده می‌شود. دلیل: محصول PlanCard هم از همین شناسه پیدا می‌شود، و mapper لازم نیست چیزی منتقل کند.
- یک تابع خالص در ماژول `catalog`، `familyMembers(byId, familyId)`:
  - اگر `familyId` تهی باشد، `[]` برمی‌گرداند.
  - در غیر این صورت رکوردهای `byId` با همان `familyId` را با ترتیب §۳ برمی‌گرداند.
  - null و undefined هم‌خانواده نیستند.
- مودال `state.byId` را از `useCatalogData()` می‌گیرد. این همان منبعی است که آنلاین/آفلاین را از قبل انتخاب می‌کند، پس شاخهٔ آفلاین جدا لازم نیست.
- **تازگی:** بازشدن مودال `catalogCoordinator.resume()` را صدا می‌زند، که خودش تا ۱۲۰ ثانیه throttle دارد. polling و query جدید اضافه نمی‌شود.
- **sweep ناقص:** اگر `state.complete` هنوز false است، اعضای موجود نمایش داده می‌شوند و با پیشرفت sweep تکمیل می‌شوند. ادعای «همهٔ گزینه‌ها» در متن نیست.
- `structuralOfflineData`/digest آفلاین فیلد `familyId` را حذف نمی‌کند. با تست قبل/بعد تأیید شود.
- **حذف از پلن قبلی:** متد `family` در coordinator، `useCatalogFamily`، query key خانواده و کل §۵.۱ و §۵.۲.

### ۴.۴ Web: مودال و نمایش

**بدون تغییر نسبت به پلن قبلی، §۵.۳ و §۵.۴**: prop `onViewProduct`، دو callsite (ProductListView و PlanCard)، اینکه مودال state مستقل ندارد، reset گالری/QR/zoom، دست‌نخوردن سبد و انتخاب، و جای بخش، عنوان، پنهان‌شدن زیر دو عضو، نشان «در حال مشاهده»، ردیف متنی، `bdi` برای SKU، masking موجودی و RTL.

تنها تغییر: ترتیب ردیف‌ها طبق §۳ است (نام، ابعاد، درجه، id)، نه «نام سپس id».

اسکیس ردیف:

```
گزینه‌های دیگر این محصول
  آلاوس سفید مات    ۱۲۰×۱۲۰  درجه ۱  <قیمت/واحد>  <وضعیت>   [مشاهده]
  آلاوس سفید مات    ۱۲۰×۲۸۰  درجه ۱  <قیمت/واحد>  <وضعیت>   ● در حال مشاهده
  آلاوس سفید پولیش  ۱۲۰×۲۸۰  درجه D  <قیمت/واحد>  <وضعیت>   [مشاهده]
```

### ۴.۵ Catalog عمومی

**بدون تغییر نسبت به پلن قبلی، §۶**، به‌جز این موارد:

- **قرارداد:** خروجی عملیات `product` در `packages/contract/src/public-catalog.ts` فیلد اجباری `familyOptions: PublicCatalogFamilyOption[]` می‌گیرد. ورودی تغییر نمی‌کند، پس flag ندارد. `PublicCatalogFamilyOptionSchema` همان `pick` پلن قبلی است.
- **CMS:** در `product` سرویس، پس از مجازشدن مبدأ:
  - مبدأ بدون طرح: `familyOptions: []`.
  - مبدأ با طرح: یک query با `compilePolicy(settings)` و `familyId` اجرا می‌شود، با شرط پارامتری `p.family_id = $n` کنار شرط نهایی انتشار، بدون `applyVisitorFilters` و با limit=100.
  - اگر total از ۱۰۰ بیشتر شد، خطای صریح سرویس برگردد، بدون truncate.
  - اعضا از `hydrate` و `mapPublicProduct` موجود رد می‌شوند و فیلدهای option صریحاً انتخاب می‌شوند.
  - خطای خواندن خانواده، خطای واقعی پاسخ است و به array خالی تبدیل نمی‌شود.
- **ترتیب در UI:** طبق §۳، در خود component و با comparator ثابت.
- **حذف از پلن قبلی:** flag `includeFamilyOptions`، حالت دوگانهٔ خروجی، تست سازگاری بدون flag و حلقهٔ صفحه‌بندی.
- **باقی موارد:** `_product-family-options.tsx`، لینک `/p/{id}`، `aria-current`، نبودِ prefetch گسترده، الزامات hidden/unpriced/amount و hidden/status/numeric، ISR ۳۰۰ثانیه، noindex و metadata بدون قیمت یا موجودی، همگی طبق پلن قبلی‌اند.

## ۶. معیارهای پذیرش

fixtureهای ساختگی محلی طبق پلن قبلی، §۸: طرح F با A/B/C، طرح G با D، U بدون طرح، و C غیرفعال.

| سناریو | نتیجهٔ لازم |
| --- | --- |
| انتقال A از F به G | A فقط در G؛ B در F می‌ماند |
| حذف طرح خالی / دارای عضو غیرفعال | اولی موفق؛ دومی رد |
| داده پس از migration | همهٔ رکوردها حفظ، `family` خالی (count/digest) |
| Edit many روی چند کالا | همه به طرح انتخابی وصل شوند [مشاهده در ادمین] |
| کاربر محدود به دستهٔ A | عضو خارج دسته در `byId` نیست و در مودال نمی‌آید |
| C غیرفعال | در Web نمی‌آید |
| جست‌وجوی صفحه فقط A را یافته | B همچنان در گزینه‌های مودال دیده شود |
| بستهٔ آفلاین جدید / قدیمی | جدید: اعضای بسته؛ قدیمی: بدون بخش و بدون خطا؛ هیچ درخواست شبکه |
| تغییر `familyId` در digest آفلاین | نسخهٔ ساختاری تغییر را ببیند |
| کلیک سریع A→B→A | متن، قیمت، گالری، QR و action متعلق به عضو فعال |
| انتخاب A، مشاهدهٔ B | انتخاب A حفظ شود؛ اقدام انتخاب روی B انجام شود |
| مودال از PlanCard | تغییر گزینه مجاز؛ خرید غیرفعال؛ طرح تخفیف به B تعمیم نیابد |
| Catalog با exclusions/additions | فقط اعضای منتشرشدهٔ همان طرح؛ addition غیرعضو وارد نشود |
| Catalog قیمت hidden/amount/unpriced و موجودی hidden/status/numeric | JSON و DOM فقط حالت مجاز را نشان دهند |
| مبدأ عمومی 404 یا pause | `CATALOG_NOT_FOUND`، بدون افشای اعضا |
| طرح بیش از ۱۰۰ عضو (unit) | خطای صریح، نه truncate |
| بدون طرح یا تک‌عضو | بخش در هر دو UI پنهان |
| ۳۷۵px، نام بلند، صفحه‌کلید | بدون overflow افقی؛ focus، bidi و نام کنترل درست |

## ۷. انتشار و بازگشت

- همهٔ appها با یک deploy منتشر می‌شوند. feature با جدول خالی طرح‌ها قابل انتشار است.
- گروه‌بندی واقعی کار جداگانهٔ مدیر با Edit many است.
- rollback با نسخهٔ برنامه انجام می‌شود. migration down دستور rollback تولید نیست.
- گزارش اجرا در `.agents/brain/product-families-execution-report.md` طبق پلن قبلی، §۹.
