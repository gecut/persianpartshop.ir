# پلن کاتالوگ مشترک، درخواست تأمین بدون منبع و تاریخچهٔ یکپارچه

تاریخ: ۲۰۲۶-۱۱-۰۸
مبنای بررسی کد: `11693c0`؛ پیش از اجرا تغییرات بعدی را بررسی کنید.
وضعیت: فقط پلن؛ هیچ تغییر کد، migration یا عملیات پروداکشن با نوشتن این سند اجرا نشده است.
مخاطب: agent اجراکننده؛ این سند باید بدون نیاز به تاریخچهٔ گفتگو قابل اجرا باشد.

## ۱. اختیار و اولویت تصمیم‌ها

- دستور جدید کاربر: پروژه پروداکشن است و داده باید حفظ شود. فرض قبلی «هر بار volumeها پاک می‌شوند» برای این تغییر معتبر نیست.
- **هیچ baseline موجودی حذف یا بازنویسی نشود؛ migration جدید افزایشی باشد.** `migrate:fresh`، reset، truncate، حذف volume و seed نمایشی روی پایگاه عملیاتی ممنوع‌اند.
- درخواست فعلی فقط تهیهٔ پلن است. اجرای بعدی کد و انتشار باید طبق دستور اجرای کاربر باشد؛ این سند به‌تنهایی مجوز استقرار نیست.
- خواستهٔ جدید جایگزین تصمیم قدیمی «یک محصول و یک انبار در درخواست» می‌شود: هر درخواست جدید یک محصول و مقدار دارد، بدون انتخاب یا تخصیص خودکار انبار.
- تأیید تکمیلی کاربر: حالت‌های جداگانهٔ خرید/تأمین از بالای محصولات حذف شوند؛ مسیر مناسب پس از تعیین مقدار مشخص شود. صفحهٔ «درخواست‌ها و سفارش‌ها» سوابق را در یک فهرست زمانی با کارت‌های هماهنگ نشان دهد.
- قواعد قیمت، بسته‌بندی، پالت، مجوز خرید، پنج وضعیت، لغو قبل از بررسی، مهلت ۴۸ ساعت و SMS نهایی تغییر نکنند.
- پوش به `main` می‌تواند CI/CD و webhook Dokploy را فعال کند؛ تا پایان گیت‌های migration پوش به main انجام نشود.

## ۲. رفتار مورد انتظار

مسیر اصلی مشتری: جست‌وجوی محصول در کاتالوگ مشترک → بازکردن محصول → تعیین مقدار → بررسی سرور → افزودن به سفارش یا ثبت درخواست تأمین با اقدام صریح مشتری.

مشتری محصول، مقدار و یادداشت اختیاری را وارد می‌کند. فقط وقتی درخواست مجاز است که:

۱. حساب و محصول طبق مجوزهای فعلی قابل سفارش باشند.
۲. دست‌کم یک رابطهٔ فعال میان محصول و یک انبار فعال از نوع inquiry وجود داشته باشد.
۳. هیچ انبار فعال exact به‌تنهایی مقدار لازم پس از گردکردن بسته‌بندی را نداشته باشد.

وجود محصول در چند انبار استعلامی فقط یک امکان ثبت ایجاد می‌کند؛ درخواست چندگانه ساخته نمی‌شود. نام یا شناسهٔ انبارها به مشتری عرضه نمی‌شود. هیچ انباری خودکار برای درخواست جدید انتخاب نمی‌شود. بررسی منابع وظیفهٔ داخلی مجموعه است؛ تخصیص منبع نهایی و گردش‌کار تازه جزو این تغییر نیست.

## ۳. مدل دادهٔ هدف — تصمیم اجرایی ثابت

«منبع تأمین» به‌عنوان collection و منوی عملیاتی مستقل حذف می‌شود، اما دانستن اینکه هر انبار چه محصولاتی دارد همچنان ضروری است.

برای پرهیز از ساختن collection دیگری با همان معنی، collection موجود `warehouse-stock` به فهرست واحد «محصولات انبار» تبدیل شود:

| ویژگی | انبار exact | انبار inquiry |
|---|---|---|
| رابطهٔ warehouse × product | یکتا | یکتا |
| inventorySqm | عدد نامنفی با دو رقم اعشار، اجباری | null؛ مقدار ناشناخته است |
| revision | همان نسخهٔ موجودی | صفر؛ وارد مسیر اصلاح موجودی نمی‌شود |
| isActive جدید | برای ردیف‌های قدیمی true؛ در exact قابل تغییر نباشد | فعال/غیرفعال بودن امکان استعلام |
| lastReportedAt جدید | null | تاریخ گزارش حضور محصول؛ از دادهٔ قبلی حفظ شود |
| stockCartons مجازی | همان محاسبهٔ فعلی | null؛ هرگز صفر به معنای موجودی قطعی نمایش داده نشود |

- مقدار صفر موجودی exact با «امکان استعلام» برابر نیست.
- رابطهٔ inquiry در CMS از همان محصولات انبار مدیریت شود؛ فیلد مقدار برای آن مخفی/غیرقابل ورود و در سرور نیز ممنوع باشد.
- مقادیر مثبت inquiry هرگز با null جایگزین نشوند مگر preflight نشان دهد چنین داده‌ای وجود ندارد؛ مشاهدهٔ آن نشانهٔ ناسازگاری و مانع migration است.
- شناسه، مقدار، revision و timestamps تمام ردیف‌های exact قدیمی عیناً حفظ شوند.
- تبدیل exact ↔ inquiry برای انبار دارای سابقه همچنان ممنوع بماند.
- فقط manager و superadmin رابطهٔ inquiry را مدیریت کنند. service فقط دسترسی لازم خواندن داشته باشد؛ support مجوز مدیریت موجودی یا رابطه نگیرد.

### درخواست‌های قدیمی و جدید

- `warehouse`، `warehouseName` و `warehouseCode` در جدول supply_requests nullable شوند؛ برای درخواست‌های جدید همگی null باشند.
- مقدار قبلی این ستون‌ها در تمام درخواست‌های تاریخی حفظ و غیرقابل ویرایش بماند. برچسب CMS: «انبار ثبت‌شده در درخواست قدیمی».
- نمایش مشتریِ جدید انبار را نشان ندهد؛ این تاریخچه برای مدیریت و حفاظت داده باقی بماند.
- شناسه‌ها، شماره‌ها، وضعیت‌ها، مقدارها، قیمت‌ها، snapshotها، deadlineها و timestamps درخواست‌های قبلی تغییر نکنند.
- `fingerprintVersion` جدید برای سوابق قبلی 1 و برای ثبت جدید 2 باشد. صرفاً default دیتابیس را مبنای تشخیص نسخه نگذارید؛ مسیر create نسخهٔ 2 را صریح تعیین کند.

## ۵. مرحله A — ثبت وضعیت و آماده‌سازی آزمایش

۱. git status و commit مبنا را ثبت و کار نامرتبط را حفظ کنید؛ پوشهٔ `output/` هنگام بررسی این پلن untracked بود و جزو این تغییر محسوب نمی‌شود.
۲. migrationهای نسخهٔ مستقر و جدول payload_migrations را با artifact مستقر تطبیق دهید. فعلاً در مخزن `20261108_152041_baseline` وجود دارد؛ از روی نام آن حدس نزنید روی سرور هم همین اجرا شده است.
۳. اگر تاریخچهٔ مستقر با مخزن فرق دارد، توقف کنید؛ راه‌حل با حذف history یا جا زدن baseline جدید ممنوع است.
۴. از پایگاه عملیاتی backup سازگار PostgreSQL شامل schema، data و sequenceها گرفته شود؛ آن را در مقصد جدا بازیابی و سالم بودن restore اثبات کنید. دادهٔ شخصی و secret در مخزن/گزارش نیاید.
۵. تعداد و checksum مرتب‌شده بر اساس PK برای جدول‌های حساس، sequence state و orphanها ثبت شوند. صرف count برای حفظ داده کافی نیست.
۶. آزمون‌ها فقط با URI صریحِ پایگاه موقت اجرا شوند. `test:hardening:postgres` fixture تخریبی دارد و نباید به clone ارزشمند یا production اشاره کند.

خروجی الزامی: فهرست migrationهای واقعی، artifact backup بازیابی‌شده، گزارش preflight و URIهای تست بدون credential. تا موفقیت این مرحله اجرای migration عملیاتی ممنوع است.

## ۶. مرحله B — CMS و جداسازی مسیر خرید

۱. مدل محصولات انبار مطابق بخش ۳ تغییر کند. null را با `Number(null)` به صفر تبدیل نکنید.
۲. create/update رابطهٔ inquiry از سرور نوع انبار را بررسی و warehouse را در تراکنش lock کند. warehouse و product ردیف موجود تغییرپذیر نباشند.
۳. اصلاح مقدار exact فقط از مسیر کنترل‌شدهٔ فعلی انجام شود؛ بازکردن update عمومی برای مدیریت inquiry نباید امکان دورزدن revision، رزرو یا import را بدهد.
۴. تمام queryهای مقدار موجودی خرید، quote، جمع موجودی، import، رزرو و بازگردانی فقط exact را مصرف کنند. کاتالوگ مشترک محصول inquiry را هم نمایش می‌دهد، اما مقدار موجودی را از inquiry استخراج نمی‌کند. شرط amount > 0 به‌تنهایی جای شرط نوع انبار نیست.
۵. hook محافظ نوع انبار به ردیف‌های جدید نگاه کند و وابستگی فعال به supply_sources را حذف کند؛ ارجاع درخواست تاریخی همچنان بررسی شود.
۶. eligibility ثبت تأمین در CMS از وجود رابطهٔ فعال inquiry استخراج شود؛ client/API مرجع نهایی اعتبارسنجی نیستند.
۷. source/warehouse هنگام create به‌صورتی lock شوند که غیرفعال‌سازی همزمان، ثبت نامعتبر نسازد؛ ترتیب lock با مسیرهای موجود سازگار باشد. صحت آن با race test ثابت شود.
۸. collection عملیاتی SupplySources از config حذف شود؛ جدول legacy در migration طبق بخش ۱۰ آرشیو می‌شود، نه اینکه اطلاعاتش حذف شود.
۹. types و import map با فرمان‌های پروژه تولید شوند؛ فایل تولیدی با دست ویرایش نشود.

## ۷. مرحله C — قرارداد و تکرار امن ثبت

- preview همچنان quote و eligible/reason بدهد، اما فهرست warehouses ندهد.
- نام داخلی خطا `SOURCE_UNAVAILABLE` / `no_active_source` می‌تواند برای سازگاری موقت بماند؛ متن مشتری «امکان درخواست تأمین برای این محصول فعال نیست» باشد.
- ورودی جدید submit محصول، مقدار، یادداشت و idempotencyKey دارد؛ warehouse ورودی عملیاتی نیست.
- برای سازگاری با تب‌ها/کلاینت‌های قدیمی، warehouseId اختیاری و deprecated موقتاً پذیرفته شود؛ فقط برای تشخیص replay نسخهٔ قدیم استفاده شود. از این مقدار برای تعیین انبار درخواست جدید استفاده نشود.
- fingerprint نسخهٔ ۱ دقیقاً الگوریتم فعلی شامل productId، warehouseId، quantity و notes.trim است؛ hashهای قبلی بازنویسی نشوند.
- fingerprint نسخهٔ ۲ شامل محصول، مقدار و notes.trim است؛ بدون warehouse. hash کلید همچنان customer-scoped باشد.
- lookup کلید ثبت‌شده قبل از eligibility انجام شود. در صورت وجود نتیجه، طبق نسخهٔ ذخیره‌شده payload بررسی شود؛ payload متفاوت conflict بگیرد.
- replay نسخهٔ ۱ با warehouseId اصلی باید همان درخواست را بدهد، حتی پس از تغییر منابع و موجودی. payload نسخهٔ ۱ بدون شناسهٔ اصلی نباید بی‌قید به موفقیت تبدیل شود؛ conflict بازیابی‌پذیر بدهد و history قابل دسترسی بماند.
- کلید قدیمی که هنوز در سرور ثبت نشده، هنگام ارسال بعدی طبق نسخهٔ ۲ ایجاد شود. این اولین ثبت است؛ کلید عوض نشود.
- پس از خطای concurrent create، lookup برنده و بررسی نسخه همچنان انجام شود؛ unique index کلید حفظ شود.
- mapper پاسخ فیلدهای منبع/انبار داخلی را از DTO مشتری حذف کند و nullable تاریخی را بدون crash بخواند.
- مالکیت list/detail/cancel و لغو اتمیک در رقابت با review حفظ شوند.

## ۸. مرحله D — draft و رابط مشتری

۱. انتخاب، نام و توضیحات انبار از فرم و history مشتری حذف شوند. مقدار، یادداشت و برآورد باقی بمانند.
۲. draft جدید warehouseId نداشته باشد. draft ذخیره‌شدهٔ قدیمی parse شود؛ اطلاعات warehouseId قدیمی فقط به‌عنوان metadata موقت بازیابی حفظ شود.
۳. برای draft غیرpending قدیمی، حذف انتخاب انبار نباید مقدار، یادداشت یا سبد خرید را پاک کند. کلید ثبت بی‌دلیل تغییر نکند.
۴. برای draft pending قدیمی، کلید و ورودی قبلی از جمله warehouseId legacy تا تعیین نتیجه حفظ شوند؛ banner بازیابی مستقل از eligibility و دسترسی preview باقی بماند.
۵. تغییر نسخهٔ draft بدون migration آن یا پاک‌کردن localStorage ممنوع است. آزمون reload و خطای شبکه اجباری است.
۶. فرم فقط وقتی preview معتبر و eligible است ثبت تازه کند؛ retry یک pending ناشناخته به preview وابسته نباشد.
۷. mode و تب بالای کاتالوگ حذف شوند؛ کاتالوگ مشترک مطابق بخش ۸.۱ باشد. حالت قدیمی URL/local state به نمای مشترک هدایت شود و هیچ draftی پاک نشود.
۸. قرارداد رزرو و سبد خرید حفظ شود؛ هماهنگی UX مطابق بخش ۸.۱ است. نام انبار خرید و انتخاب انبار قطعی را حذف نکنید.

### ۸.۱ کاتالوگ واحد و تصمیم پس از تعیین مقدار

این بخش مصوب است و جایگزین خرید/تأمین به‌صورت دو حالت مستقل کاتالوگ می‌شود.

۱. همهٔ محصولات فعال و مجاز در یک جست‌وجو نمایش داده شوند؛ موجودی صفر باعث حذف پیش‌فرض محصول نشود. «فقط موجودها» فیلتر اختیاری باشد. محصول غیرفعال یا خارج از مجوز دسته نمایش داده نشود.
۲. نشانهٔ کارت فقط راهنماست: «موجود» برای موجودی قطعی حداقل یک بسته/واحد فروش؛ «قابل استعلام» اگر موجودی قابل فروش ندارد و رابطهٔ inquiry فعال دارد؛ «فعلاً ناموجود» در غیر این صورت. محصولی که هر دو امکان را دارد نشانهٔ «موجود» بگیرد؛ قابلیت تأمین آن در داده حفظ شود.
۳. وضعیت نشانهٔ کارت برای مقدار خاص قول قطعی نیست. مقدار موردنیاز کاربر بعد از گردکردن بسته‌بندی در سرور بررسی شود؛ موجودی مثبت به معنی کفایت برای هر مقدار نیست.
۴. ورودی مقدار در مسیر محصول یک نقطهٔ روشن و مشترک داشته باشد. همان مقدار و یادداشت هنگام تغییر مسیر حفظ شوند. اگر مقدار در صفحهٔ سفارش چندمحصولی هم قابل تغییر است، همان کنترل کفایت آنجا نیز اجرا شود؛ مسیر فرعی نباید کمبود را دور بزند.
۵. نتیجهٔ کافی‌بودن موجودی یک exact → اقدام «افزودن به سفارش» و ادامهٔ انتخاب انبار قطعی فعلی. نتیجهٔ کمبود + امکان inquiry → اقدام «درخواست تأمین». نتیجهٔ کمبود بدون inquiry → پیام روشن و بدون دکمهٔ ثبت فعال.
۶. درخواست تأمین برای **کل مقدار واردشده** است. خرید بخشی از موجودی + تأمین خودکار کسری، ثبت همزمان دو رکورد و تجمیع موجودی چند انبار خارج دامنه‌اند.
۷. خرید چندمحصولی حفظ شود. انتقال یک محصول از انتخاب خرید به draft تأمین فقط با اقدام صریح باشد؛ بقیهٔ اقلام حذف نشوند. اگر محصول از قبل در خرید است، تأمین خودکار آن خط را حذف/تغییر ندهد؛ به کاربر وجود آن در draft خرید اعلام شود.
۸. دو draft خرید و تأمین همچنان مستقل‌اند؛ «فرم مشترک» به معنی ادغام storeها یا ارسال مشترک آن‌ها نیست. تأمین فعلاً همان یک محصول است و جایگزینی محصول draft با تأیید فعلی انجام شود.
۹. تغییر مقدار نتیجهٔ بررسی قبلی را stale کند؛ پاسخ دیررس مقدار قبلی نباید اقدام اشتباه را فعال کند. loading/error شبکه با «ناموجود» اشتباه نشود. تا بررسی معتبر اقدام ثبت جدید فعال نباشد.
۱۰. موجودی/eligibility هنگام submit دوباره بررسی شوند. اگر مسیر لازم عوض شد، مقدار و یادداشت حفظ، علت اعلام و اقدام مناسب به مشتری پیشنهاد شود؛ هیچ نوع ثبت بدون کلیک تازهٔ مشتری تبدیل نشود. pending مبهم طبق بخش ۷ ابتدا replay می‌شود.
۱۱. کاربر فقط‌کاتالوگ همچنان امکان ثبت هیچ نوع درخواست یا سفارش ندارد؛ نشانه‌ها نباید مجوز را دور بزنند یا موجودی پنهان را افشا کنند.
۱۲. «محصول در نتایج پیدا نشد» فقط راهنمای اصلاح جست‌وجو/فیلتر داشته باشد؛ فرم کالای خارج کاتالوگ به این پروژه اضافه نشود.

خروجی API کاتالوگ باید قابلیت استعلام و وضعیت موجودی مجاز را بدون فهرست/نام انبار inquiry فراهم کند. shape فقط در contract تعریف شود. برای تعیین مسیر بر اساس مقدار، از quote خرید موجود و preview تأمین با ownership روشن استفاده کنید؛ business rule جدید در browser بازنویسی نشود. با کافی بودن exact، preview تأمین نباید شرط افزودن به خرید شود.

### ۸.۲ feed مشترک «درخواست‌ها و سفارش‌ها»

**مدل‌های ذخیره‌سازی جدا می‌مانند؛ فقط خواندن و نمایش مشترک می‌شود.** انتقال سفارش‌ها و درخواست‌ها به یک جدول یا یکسان‌سازی state machineها خارج دامنه است.

۱. عنوان صفحه و عنوان کامل ناوبری به «درخواست‌ها و سفارش‌ها» تغییر کند. در عرض کم عنوان با wrap مناسب نمایش یابد؛ متن نامفهوم یا بریده نسازید.
۲. پیش‌فرض یک feed شامل هر دو نوع است. تب اجباری جدا حذف شود؛ فیلتر اختیاری «همه / سفارش / درخواست تأمین» در دسترس باشد.
۳. feed تازه در contract به‌صورت discriminated union با `kind: order | supply` تعریف شود؛ نوع رکورد و شناسه با هم هویت یکتا هستند. موجود بودن order 42 و supply 42 نباید برخورد key، navigation یا cache بسازد.
۴. ترتیب قطعی سرور: createdAt نزولی، سپس kind با ترتیب ثابت مستند، سپس شناسه نزولی. updatedAt مبنای ترتیب نیست؛ تغییر وضعیت کارت را بالا نمی‌آورد. تاریخ نامعتبر به Date.now تبدیل نشود.
۵. صفحه‌بندی **مشترک در سرور** انجام شود؛ گرفتن page اول هر دو list و چسباندن آن‌ها در browser ممنوع است. API از یک endpoint داخلی خواندن در CMS از طریق SDK استفاده کند؛ query پارامتری UNION ALL در CMS از داده‌های مالک فعلی در دو جدول اجرا شود، در آن فیلتر/ترتیب/limit اعمال می‌کند و شناسه‌ها را برای mapping به DTOهای مجاز hydrate می‌کند. از join اقلام سفارش برای صفحه‌بندی استفاده نکنید؛ هر سفارش دقیقاً یک entry است.
۶. cursor opaque و اعتبارسنجی‌شده شامل tuple آخرین رکورد و watermark شروع traversal باشد. cursor با filter ناسازگار رد شود. userId همیشه از session تعیین شود، نه cursor. traversal از نظر createdAt تازه‌تر از watermark رکورد نگیرد؛ رکوردهای تازه پس از refresh ظاهر شوند. backdated insert و تغییر عضویت فیلتر وضعیت تضمین snapshot کامل ندارند؛ در گزارش محدودیت صریح شود. تغییر نوع فیلتر، pagination را از ابتدا آغاز کند.
۷. hydration نباید ترتیب query را عوض کند؛ entityها بعد از دریافت به ترتیب tupleهای اولیه چیده شوند. ownership هم در query مشترک و هم در خواندن سند رعایت شود. API برای این کار اتصال مستقیم جدید به PostgreSQL نسازد؛ مرز مالکیت CMS حفظ شود. endpoint داخلی فقط برای service مجاز باشد و هویت مشتری در API از session تعیین شود؛ مرورگر حق تعیین userId برای این endpoint ندارد. raw SQL فقط read و پارامتری باشد؛ از DTO صریح، جلوگیری از PII و stock پنهان عبور نکند.
۸. نتیجه items/nextCursor/hasMore بدهد؛ infinite query با کلید شامل owner و filter مصرف شود. مجموع‌های نمایشی از طول یک صفحه استخراج نشوند. اگر count لازم نیست به قرارداد اضافه نشود.
۹. mapper سفارش فعلی، مجوزها، قیمت‌های snapshot و قابلیت پیگیری/تکرار دوباره مصرف شوند؛ listهای قدیمی در دورهٔ سازگاری باقی بمانند. query keys نوع‌دار و owner-scoped باشند؛ خروج حساب cache حساب قبل را نشان ندهد.
۱۰. لغو/ثبت/تغییر وضعیت، feed و detail مربوط را invalidate کند. در client برای کنار هم گذاشتن نتایج pagination، مرتب‌سازی مستقل یا حدس total انجام نشود.
۱۱. فیلتر وضعیت مشترک تازه در این تغییر اضافه نشود؛ state machineهای سفارش و تأمین با هم یکی نیستند. فیلتر وضعیت فعلی سفارش فقط هنگام فیلتر نوع «سفارش» قابل نگهداری است؛ روی «همه» یا «تأمین» وضعیت سفارش اعمال نشود. تغییر نوع، وضعیت ناسازگار را پاک کند.
۱۲. لینک سفارش `/orders/$id` همچنان معتبر باشد. لینک فعلی پیامک `/orders?view=supply&requestId=...` باید حتی اگر رکورد در صفحهٔ لودشده نیست detail همان درخواست متعلق به مشتری را باز کند. لینک قدیمی به feed مشترک resolve شود، نه تب حذف‌شده. با بستن detail به feed برگردد؛ ارسال پیامک و URLهای قبلی شکسته نشوند.

### ۸.۳ کارت مشترک با تفاوت‌های محدود و معنادار

- ساختار مشترک: نوار شماره/نوع/وضعیت، تاریخ، تصویر محصولات، خلاصهٔ تعداد و مقدار، مبلغ، «پیگیری».
- عنوان شماره در هر دو نوع «شماره» باشد؛ شمارهٔ واقعی سفارش/درخواست حفظ شود و format شناسهٔ سفارش روی شمارهٔ تأمین تحمیل نشود.
- تفاوت ثابت اول: نشان «سفارش» یا «درخواست تأمین». تفاوت ثابت دوم: «مبلغ کل» یا «برآورد هزینه». ظاهر پایه، spacing، رنگ‌های معنایی و typography مشترک باشند.
- اشتراک کارت در لایهٔ ارائه باشد؛ business logic و عملیات نوع‌های مختلف یکی نشوند. مدل نمایشی از union قرارداد مشتق شود، نه type assertion و تبدیل supply به Order جعلی.
- وضعیت واقعی هر نوع نگاشت مستقل داشته باشد. «تأمین شده» = نتیجهٔ مثبت بررسی تأمین؛ نه سفارش ثبت‌شده، پرداخت‌شده یا تحویل‌شده. deadline تأمین ۴۸ ساعت است، رفتار زمانی سفارش را روی آن اجرا نکنید.
- «پیگیری» برای هر دو وجود داشته باشد. «تکرار» سفارش همان مسیر خرید فعلی؛ برای تأمین در این تغییر دکمهٔ تکرار جدید اضافه نشود. لغو و دسترسی هر نوع از سرور بیاید.
- تک‌محصولی بودن supply با همان خلاصهٔ عمومی «۱ محصول» و مقدار با واحد صحیح نمایش یابد؛ پالت صرفاً معادل نمایشی است.

خروجی این مرحله: catalog مشترک و flow مقدارمحور، feed مشترک server-paginated، کارت هماهنگ و لینک‌های قدیمی سالم.

## ۹. مرحله E — seed و مستندات

- seed فعلیِ محافظت‌شده، رابطه‌های inquiry را در محصولات انبار با مقدار null بسازد؛ ایجاد supply-sources حذف شود.
- seed دو بار روی پایگاه تازه اجرا و عدم ایجاد تکرار بررسی شود. seed جای migration دادهٔ پروداکشن نیست.
- درخواست نمایشی جدید warehouse نداشته باشد؛ نقش‌های صریح service/support تغییر نکنند.
- fixture تاریخچه شامل سفارش و تأمین با تاریخ‌های درهم‌تنیده، تاریخ مساوی و شناسهٔ عددی یکسان باشد تا feed و کارت قابل بررسی باشند.
- docs/01 تا docs/07 و گزارش اجرای تازه به رفتار جدید و الزام migration افزایشی اشاره کنند. اسناد تاریخی را طوری بازنویسی نکنید که انگار نسخهٔ قدیمی هرگز وجود نداشته است.

## ۱۰. طراحی migration افزایشی و حفاظت داده — گیت اصلی

### ۱۰.۱ قواعد تولید

- migrationهای قبلی immutable هستند؛ فایل baseline موجود و hash آن در پایان باید با ابتدای کار برابر باشد.
- یک migration جدید با نام توصیفی اضافه شود؛ تولید خودکار فقط پیش‌نویس است و SQL باید خط‌به‌خط بازبینی شود.
- تست فعلی `assert.equal(migrations.length, 1)` اصلاح شود: انتظار baseline + migration جدید و سناریوی upgrade واقعی داشته باشد. حذف این assert به‌تنهایی آزمون upgrade محسوب نمی‌شود.
- SQLهایی مثل DROP TABLE، DROP COLUMN، CASCADE، تغییر نوع، NOT NULL، unique index و FK به‌طور مستقل بررسی و دلیل هرکدام ثبت شود.
- این انتشار هیچ حذف دائمی supply_sources، snapshot انبار یا اطلاعات مدیریتی قبلی ندارد. حذف فیزیکی آرشیو به انتشار مستقل و خارج دامنه موکول شود.

### ۱۰.۲ preflight اجباری در clone و هنگام استقرار

پیش از اولین mutation، خطاهای زیر را با تعداد و نمونهٔ شناسهٔ غیرحساس گزارش و migration را متوقف کنید:

- source بدون محصول یا انبار، warehouse غیرinquiry، warehouse/product ناموجود، زوج تکراری.
- ردیف warehouse_stock متعلق به inquiry در مدل قبلی؛ به‌خصوص دارای مقدار غیرnull یا revision غیرصفر. داده را با حدس اصلاح نکنید.
- برخورد زوج source با زوج warehouse_stock موجود؛ upsert با overwrite یا ON CONFLICT DO NOTHING ممنوع است چون می‌تواند داده را پنهانی از بین ببرد.
- fingerprintVersion ناسازگار، orphan در requestها یا مقدارهای نامعتبر existing stock.
- نبودن ستون‌ها، constraintها یا migrationهای مورد انتظار؛ این وضعیت را «قبلاً اجرا شده» فرض نکنید.

وجود انبار/product غیرفعال خطا نیست؛ رابطه باید با همان وضعیت منتقل شود تا فعال‌سازی آینده معنی قبلی را حفظ کند.

### ۱۰.۳ ترتیب منطقی UP

۱. در maintenance window نویسنده‌های CMS/API و jobهای مرتبط متوقف شوند. transaction دیتابیس با lockهای لازم جلوی نویسندهٔ جا‌مانده را بگیرد؛ وجود این lockها جای قطع ترافیک برنامهٔ قدیمی را نمی‌گیرد.
۲. preflight در همان transaction تکرار شود تا بین بررسی و copy شکاف نباشد.
۳. `inventory_sqm` nullable شود؛ constraint نامنفی/دو رقم اعشار برای exact حفظ شود. null برای exact در hook و مسیرهای کنترل‌شده رد شود. قیود بین‌جدولی را با CHECK معمول PostgreSQL پیاده نکنید.
۴. ستون‌های is_active و last_reported_at به warehouse_stock افزوده شوند؛ exactهای فعلی active=true و زمان گزارش null بمانند. revision و زمان‌های قبلی تغییر نکنند.
۵. همهٔ sourceها شامل inactiveها با INSERT … SELECT به warehouse_stock منتقل شوند: warehouse/product عیناً، inventory=null، revision=0، is_active/last_reported_at/created_at/updated_at عیناً حفظ شوند. PKهای موجود warehouse_stock حفظ شوند؛ ردیف جدید شناسهٔ تازه بگیرد.
۶. جدول supply_sources با تمام ستون‌ها و IDهای قبلی، به نام ثابت `supply_sources_legacy` آرشیو شود. mapping شناسهٔ legacy به شناسهٔ جدید محصولات انبار در یک جدول migration-owned حفظ شود تا صحت copy و rollback قابل اثبات باشد. mapping ردیف‌به‌ردیف ساخته شود، نه براساس ترتیب INSERT.
۷. روابط Payload locked-documents و FKهای وابسته بررسی شوند. rename جدول PostgreSQL معمولاً target FK را حفظ می‌کند؛ نام و referent واقعی را در clone بررسی کنید. آرشیو و mapping خارج از metadata Payload هستند؛ generator نباید در migration بعدی خودسرانه آن‌ها را drop کند. این استثنا مستند شود.
۸. warehouse_id/name/code درخواست nullable و fingerprint_version افزوده شود. همهٔ سوابق فعلی نسخهٔ ۱ باشند؛ hash، snapshot و deadline دست نخورند.
۹. تمام قیود و indexهای خرید، موجودی، سفارش و درخواست باقی بمانند؛ unique warehouse×product روی مدل واحد حفظ شود. sequence ردیف جدید از max(id) جلوتر باشد و create بعدی برخورد نکند.
۱۰. postconditionها قبل از commit اجرا شوند؛ هر اختلاف باعث rollback کامل شود.

Migration کپی داده را فقط یک بار از مسیر journal رسمی Payload اجرا کند. اجرای دوبارهٔ فرمان migrate باید no-op باشد. اگر journal missing ولی ساختار نیمه‌اعمال‌شده دیده شد، fail-fast؛ تلاش خودکار برای ترمیم ممنوع است.

### ۱۰.۴ postconditionهای الزامی

- تعداد source legacy = تعداد ردیف‌های mapping = تعداد inquiryهای منتقل‌شده.
- مقایسهٔ دوطرفهٔ دادهٔ رابطه، وضعیت و timestampها میان archive و ردیف‌های جدید با join mapping؛ صرف count کافی نیست.
- checksum تمام ستون‌های exact قدیمی با قبل برابر باشد؛ تنها ستون‌های تازه طبق default مجازند.
- checksum سفارش‌ها، اقلام، کاربران، رده‌ها، مدیران و محصولات ثابت باشد.
- checksum ستون‌های قدیمی requestها ثابت باشد؛ نسخهٔ جدید تنها تفاوت مجاز است.
- تمام FKها معتبر، orphan صفر، زوج تکراری صفر، مقدار عددی inquiry صفر مورد؛ منظور null است، نه عدد 0.
- sequenceها و ایجاد یک رکورد جدید در DB آزمایشی تست شوند.

### ۱۰.۵ DOWN و بازگشت عملیاتی

- rollback داده پس از ثبت‌های نسخهٔ جدید همیشه ممکن نیست: درخواست بدون انبار را نمی‌توان با جعل warehouse به schema قدیم برگرداند.
- DOWN قبل از هر mutation باید وجود request نسخهٔ ۲، رابطهٔ inquiry جدید یا ویرایش رابطه‌های migrated را بررسی کند. اگر بازسازی دقیق گذشته ممکن نیست، صریحاً متوقف شود؛ هیچ حذف یا انتخاب تصادفی انبار مجاز نیست.
- در تست immediately-up/down بدون write جدید، mapping فقط ردیف‌های منتقل‌شده را حذف کند، جدول archive را به نام اصلی برگرداند، nullableها/ستون‌های تازه را طبق schema قدیم برگرداند و exactها را حفظ کند.
- baseline down فقط روی DB خالی/fixture اجرا شود؛ برای rollback production استفاده نشود.
- rollback عملیاتی: توقف writerها، بازگرداندن artifact قبلی و restore backup آزمایش‌شده، با پذیرش و ثبت writeهای پس از backup. بعد از بازشدن ترافیک، forward fix معمولاً امن‌تر است؛ restore بدون تصمیم مسئول انتشار انجام نشود.

## ۱۱. ماتریس آزمون — شواهد لازم برای اعلام تکمیل

### A. آزمون پایگاه قدیمی → جدید

یک DB موقت با migrationهای **قبل از این تغییر** بسازید؛ سپس با کد/fixture قدیم داده ایجاد کنید:

- حداقل دو exact با موجودی اعشاری، revision غیرصفر، order چندقلمی رزروشده و سفارش لغوشده.
- چند inquiry، یک source فعال، یک source غیرفعال، source روی انبار غیرفعال و محصول دارای دو source.
- درخواست‌های پنج وضعیت با warehouse snapshot، hash و timestampهای مشخص.
- مدیر، service، support، کاربر با محدودیت دسته و کاربر فقط‌کاتالوگ.

پیش از upgrade manifest/checksum بگیرید؛ فقط migration جدید را اجرا کنید؛ تمام شروط بخش ۱۰.۴ را assert کنید. اجرای full chain روی DB خالی جای این آزمون را نمی‌گیرد.

همین migration روی clone بازیابی‌شده از backup نیز اجرا شود؛ زمان، lock wait و رشد داده گزارش شود. اندازهٔ داده و محدودیت maintenance window روی سرور فعلاً [UNKNOWN] است؛ بدون این شاهد اعلام آمادگی production ممنوع است.

### B. rollback و fail-fast

- UP سپس DOWN فوری روی fixture = بازگشت دقیق دادهٔ قدیم.
- بعد از درخواست نسخهٔ ۲، DOWN باید بدون هیچ تغییر داده رد شود.
- بعد از ویرایش/افزودن رابطهٔ inquiry، DOWN غیرقابل‌بازسازی باید بدون تغییر داده رد شود.
- دادهٔ خرابِ عمداً ساخته‌شده: orphan، زوج برخوردی و inquiry با stock عددی؛ UP قبل از mutation رد و snapshot اولیه ثابت بماند.
- خطای تزریق‌شده وسط copy = rollback کامل؛ جدول نیمه‌منتقل و mapping ناقص باقی نماند.
- migrate دوباره = no-op؛ نه کپی دوباره و نه تغییر hash/timestamp.

### C. رفتار CMS/API و concurrency

- یک یا چند inquiry فعال برای محصول = امکان درخواست واحد؛ هیچ source لازم نیست.
- فقط ردیف inactive، انبار inactive یا exact با موجودی صفر = مجوز تأمین ایجاد نکند.
- eligibility با مقدار گرد‌شده و بدون تجمیع موجودی چند exact محاسبه شود.
- stock inquiry هرگز وارد quote خرید، import، reservation یا restoration نشود.
- client نمی‌تواند inventory inquiry را مقداردهی، مقدار exact را null، یا نوع/warehouse ردیف را عوض کند.
- دو submit همزمان با کلید یکسان = یک request؛ کلید برابر مشتری دیگر مستقل؛ payload متفاوت conflict.
- replay نسخهٔ ۱ و ۲ بعد از تغییر stock/source با همان نتیجه؛ hashهای قدیم عوض نشوند.
- source-disable در رقابت با submit و cancel در رقابت با review، با PostgreSQL واقعی آزمایش شوند؛ نتیجه باید یکی از ترتیب‌های معتبر سریالی باشد.
- snapshot و مجوزها محفوظ؛ support فقط بررسی وضعیت؛ SMS mock و بدون ارسال واقعی.

### C.1 آزمون کاتالوگ و feed مشترک

- catalog شامل محصول با stock کافی، stock مثبت ولی کمتر از یک بسته، stock صفر با inquiry، stock صفر بدون inquiry و محصول غیرمجاز باشد؛ default هیچ نوع مجاز را به‌دلیل صفر بودن موجودی حذف نکند.
- یک محصول برای مقدار کم به خرید و برای مقدار بیشتر به تأمین برود؛ مبنا مقدار گرد‌شده باشد. نتیجهٔ خطای شبکه و پاسخ stale با ناموجود اشتباه نشود.
- feed برای دو مشتری مستقل، order و supply با ID برابر و createdAt برابر، بیش از سه صفحه و فاصله‌های زمانی نامتوازن آزموده شود؛ هر رکورد در traversal بدون write دقیقاً یک‌بار و به ترتیب ثابت ظاهر شود.
- درج رکورد تازه بین صفحات، refresh، cursor خراب، cursor ناسازگار با filter و جعل مالکیت آزمایش شوند. feed بدون hydrate همهٔ سوابق محدود به page size باشد.
- تغییر وضعیت ترتیب زمانی را عوض نکند؛ فیلتر نوع سفارش و تأمین کامل و صحیح باشد. وضعیت سفارش روی supply اعمال نشود.
- endpoint داخلی CMS با نقش غیرمجاز رد شود؛ API فیلد هویت مشتری در ورودی عمومی feed نداشته باشد. feed هیچ سند متعلق به مشتری دیگر یا فیلد حساس مدیریت را برنگرداند.
- طرح query با EXPLAIN روی clone بررسی شود؛ فقط اگر نیاز واقعی وجود دارد index افزایشی مناسب مالک/تاریخ افزوده شود. ایجاد index و مسیر DOWN آن هم جزو بازبینی migration باشد؛ برای feed جدول ذخیره‌سازی یا backfill تازه ساخته نشود.

### D. مرورگر

- صفحهٔ محصولات بدون switch خرید/تأمین؛ جست‌وجوی محصول بدون موجودی ممکن باشد و «فقط موجودها» اختیاری کار کند.
- تعیین مقدار کم/زیاد روی یک محصول، خرید/تأمین متناسب پیشنهاد دهد؛ تغییر مسیر یادداشت و مقدار را حفظ کند و ثبت خودکار نکند.
- خرید چندمحصولی، انتقال یک محصول به تأمین، باقی‌ماندن سایر اقلام و مستقل‌بودن draftها بررسی شوند؛ تأمین فقط کل مقدار را ثبت کند.
- فرم جدید بدون select انبار؛ تاریخچهٔ قدیمی/جدید بدون نمایش منبع و بدون crash.
- عنوان «درخواست‌ها و سفارش‌ها»، درهم‌بودن زمانی کارت‌ها، pagination چندصفحه‌ای، فیلتر نوع و نبود شماره/کلید برخوردی تست شوند.
- کارت سفارش و تأمین چیدمان مشترک، نوع و عنوان مبلغ صحیح داشته باشند؛ وضعیت «تأمین شده» با تکمیل سفارش یکی نشود.
- لینک SMS قدیمی به درخواست خارج صفحهٔ اول و لینک جزئیات سفارش باز شوند؛ back/close فیلتر و محل feed را تا حد امکان حفظ کند.
- پس از لغو یا ثبت، feed به‌روز شود؛ تعویض حساب اطلاعات حساب قبلی را نشان ندهد.
- draft خرید مستقل؛ draft قدیمی غیرpending حفظ مقدار و یادداشت.
- pending نسخهٔ قبل با پاسخ گم‌شده، reload و حذف eligibility همان کلید را replay کند و duplicate نسازد.
- draft pending ثبت‌نشدهٔ قدیمی با همان key یک درخواست جدید بدون warehouse بسازد.
- submit بدون منبع فعال خطای روشن بدهد و draft حفظ شود؛ موجودی کافی مسیر خرید را پیشنهاد دهد.
- موبایل و دسکتاپ، RTL، بسته‌بندی و پالت، تغییر حساب و دسترس‌پذیری keyboard بررسی شوند.

## ۱۲. فرمان‌های بررسی و قواعد اجرای آن‌ها

از ریشهٔ repo و pnpm استفاده کنید. URIها را فقط برای مقصد disposable مورد تأیید جایگزین کنید؛ credential در فایل گزارش ذخیره نشود.

```sh
pnpm --filter @persianpart/cms generate:types
pnpm --filter @persianpart/cms generate:importmap
pnpm --filter @persianpart/contract exec tsc --noEmit
pnpm --filter @persianpart/cms exec tsc --noEmit --incremental false
pnpm --filter @persianpart/api exec tsc --noEmit
pnpm --filter @persianpart/web exec tsc --noEmit
pnpm --filter @persianpart/cms test:hardening
pnpm --filter @persianpart/api test
pnpm --filter @persianpart/web build
pnpm --filter @persianpart/cms build
```

آزمون‌های زیر به env محافظت‌شدهٔ مستقل نیاز دارند؛ نبود env و skipped به معنی pass نیست:

```sh
pnpm --filter @persianpart/cms test:hardening:migrations
pnpm --filter @persianpart/cms test:hardening:postgres
pnpm --filter @persianpart/web exec playwright test e2e/pwa-supply.spec.ts e2e/pwa-warehouse.spec.ts
```

`CMS_MIGRATION_TEST_DATABASE_URI` طبق guard فعلی باید به control DB با نام postgres و loopback و port صریح اشاره کند. `CMS_TEST_DATABASE_URI` باید نام fixture مجاز cms_hardening_test داشته باشد. آزمون HTTP زندهٔ supply طبق guard داخل فایل اجرا شود؛ API test معمولی به‌تنهایی این مسیر را اجرا نمی‌کند.

CMS build و تولید schema با env موقت انجام شوند؛ هیچ ابزار dev با push خودکار به production وصل نشود. در پایان `git diff --check`، فهرست فایل‌ها و hash baseline کنترل شوند؛ artifactهای build و کارهای نامرتبط وارد commit نشوند.

## ۱۳. انتشار تولید با توقف کنترل‌شده

این تغییر schema و قرارداد API دارد. zero-downtime فرض نشود؛ تب قدیمی/PWA ممکن است مدت زیادی فعال بماند و سازگاری بخش ۷ و ۸ ضروری است.

گیت‌های قبل از انتشار:

- backup restore شده و upgrade clone با شواهد حفظ داده موفق است.
- تمام آزمون‌های بالا اجرا شده‌اند؛ skippedها صریح‌اند و lanes حیاتی تکمیل شده‌اند.
- بازبینی مستقل migration با nexload-cto-review، در صورت درخواست/مجوز delegation با sub-agent، بدون ادعای اینکه review جای اجرای migration است.
- artifactهای API/CMS/Web با یک revision مشخص آماده و tag آن‌ها قابل pin کردن باشد.
- زمان توقف، مالک rollback و دسترسی به restore مشخص باشند.

ترتیب rollout: maintenance → توقف نویسنده‌ها و jobها → backup نهایی → preflight → migration یک‌بار → postconditions → بالا آوردن نسخه‌های هماهنگ CMS/API/Web → smoke test → بازکردن ترافیک. Compose فعلی migration one-shot و prodMigrations دارد؛ journal رسمی باید مانع اجرای مجدد شود، نه دستکاری دستی journal.

Smoke test عملیاتی فقط دادهٔ آزمایشی کنترل‌شده و بدون SMS واقعی: کاتالوگ مشترک و تصمیم بر اساس مقدار، feed مشترک و لینک قدیمی SMS، خواندن درخواست تاریخی، یک درخواست جدید بدون انبار، replay همان کلید، بررسی stock exact قبل/بعد و دسترسی کارکنان. دریافت HTTP 200 یا webhook موفق اثبات اجرای migration نیست؛ journal، schema و دادهٔ واقعی بررسی شوند.

اگر migration یا postcondition شکست خورد، ترافیک باز نشود؛ از reset و seed برای «درست کردن» production استفاده نشود. گزارش خطا بدون دادهٔ شخصی تهیه و طبق rollback اثبات‌شده عمل شود.

## ۱۴. تعریف اتمام و تحویل agent

- [ ] collection/منوی عملیاتی منابع تأمین حذف و مدیریت رابطه از محصولات انبار ممکن است.
- [ ] محصول inquiry مقدار موجودی ساختگی ندارد و خرید فقط exact مصرف می‌کند.
- [ ] درخواست تازه و UI مشتری انتخاب/تخصیص انبار ندارند.
- [ ] کاتالوگ مشترک بدون mode است؛ مسیر خرید/تأمین پس از مقدار مشخص می‌شود و ثبت نیازمند اقدام صریح است.
- [ ] صفحهٔ «درخواست‌ها و سفارش‌ها» feed مشترک مرتب‌شده و صفحه‌بندی‌شده در سرور دارد.
- [ ] کارت‌ها ساختار مشترک، نوع و عنوان مبلغ متمایز دارند؛ وضعیت و عملیات هر نوع درست باقی مانده‌اند.
- [ ] لینک‌های قدیمی، pendingهای قدیمی، cursorها و هویت owner با آزمون تأیید شده‌اند.
- [ ] درخواست و draft و replay قدیمی سالم‌اند؛ هیچ سابقه‌ای پاک یا بازنویسی نشده است.
- [ ] baseline تغییر نکرده؛ migration افزایشی، archive و mapping حفظ اطلاعات دارند.
- [ ] upgrade قدیم→جدید، full fresh، fail-fast، rollback امن و clone restore همگی با شواهد انجام شده‌اند.
- [ ] آزمون واحد، PostgreSQL، HTTP زنده، مرورگر و buildهای لازم موفق‌اند.
- [ ] seed فقط روی disposable دو بار اجرا و مستندات به‌روز شده‌اند.
- [ ] گزارش اجرای جدا شامل commitها، migration name، نتایج دقیق، checksum summary، backup/restore evidence بدون secrets و محدودیت‌ها ذخیره شده است.

گزارش نهایی باید «پیاده‌سازی»، «آزمایش روی fixture»، «آزمایش clone production» و «استقرار production» را جداگانه بیان کند. agent با نبود دسترسی به production می‌تواند کد و تست محلی را کامل کند، ولی مجاز نیست گیت clone یا انتشار را انجام‌شده اعلام کند.
